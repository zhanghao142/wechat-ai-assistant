## 三、丢消息排查

### 现象回顾

用户连续发送多条消息时，部分消息无日志无回复地丢失。纯文本、图片+文字均有概率触发。

### 排查过程

| 步骤 | 做了什么 | 结论 |
|------|---------|------|
| ① | 加入全链路轮询序号日志 | 追踪到消息的唯一标识 `[POLL#seq]` |
| ② | 复现出第一张图丢、第二三张图正常 | 锁定到长轮询竞态条件 |
| ③ | 反编译 2.3.3 SDK | 确认 `GetUpdatesCursorStore` 游标推进机制 |
| ④ | 调整 readTimeoutMs 5s→10s→15s | 确认超时窗口不是根因 |

### 根因

```
POLL#6 getUpdates → 0 条 (18091ms)    ← 长轮询超时
               ↓ 用户在这期间发了第一张图
POLL#7 getUpdates → 1 条 (items=[2])  ← 只拉到了第二张图
POLL#8 getUpdates → 1 条 (items=[2])  ← 只拉到了第三张图
```

SDK 长轮询超时瞬间，服务端游标已推进但客户端超时没收到消息。下一轮用新游标请求，服务端认为那些消息已被消费过。

### 结论

**SDK 协议层设计局限**，当前版本（2.3.3，Maven Central 最新）不提供 WebSocket 推送或按消息 ID 补拉的接口。根治需要换 SDK/换方案，当前纯文本场景体验可接受。

## 四、Agent 能力验证

### 测试 1：多工具并行（★★）

用户说："南京天气怎么样？顺便看看有没有最近的AI新闻"

LLM 结果：✅

```
一次推理同时返回 2 个 tool_calls：
  queryWeather("Nanjing")
  searchInternet("AI人工智能 最新新闻 2025")
→ 执行后一次整合回复，耗时 ~5s
```

**亮点**：零代码实现了"既要又要"的意图识别和并行工具调用。

### 测试 2：链式调用 + 互联网搜索（★★★）

用户说："帮我搜一下梅西是谁，然后读一下相关信息"

LLM 结果：✅

```
① searchInternet("梅西 百度百科") → 拿到百科链接
② readUrl(百科URL) → 读正文
③ 生成回复 + [VOICE] → 语音合成发送
```

**亮点**：LLM 自主决定先搜再读，"读一下"成功触发了语音。

### 测试 3：搜索失败自适应（★★★★★）

用户说："帮我找一下2024年巴黎奥运会中国拿了多少金牌，然后读给我听"

LLM 结果：✅（过程坎坷但最终成功）

```
① searchInternet("2024年巴黎奥运会 中国 金牌数")     → 不相关
② searchInternet("巴黎奥运会 2024 中国金牌榜 总数")   → 不相关
③ searchInternet("2024巴黎奥运会中国金牌数量 40枚")  → 不相关
④ searchInternet("2024巴黎奥运会中国代表团金牌数")   → 不相关
⑤ searchInternet("巴黎奥运会 2024 中国 40枚金牌")    → 不相关
⑥ searchInternet("2024巴黎奥运会 中国 金牌 40枚")    → 不相关
⑦ readUrl(百度百科奥运会词条)                        → ✅ 拿到数据
⑧ 回复: 40金27银24铜，与美国并列第一 + [VOICE]       → ✅ 语音合成发送
```

**亮点**：连续 6 次搜索不命中后，LLM **自主切换策略**为 `readUrl` 读百科。这是 Agent 最有价值的特性——没有硬编码兜底逻辑，模型自己知道换条路走。

### 测试 4：工具组合失败（★★）

用户说："看看杭州今天的天气并查询一下那些景点适合这个天气去旅游"

LLM 结果：❌

```
queryWeather("Hangzhou") → 中到大雨
→ LLM 直接凭知识回复了景点推荐，没有再调 searchInternet
```

**根因**：System Prompt 没有告诉 LLM "可以用上一个工具的结果决定下一个工具的参数"。已补充工具组合规则。

### 测试 5：多工具并行 + 互联网搜索 + 链式调用（★★★）

用户说："帮我搜一下最近的热门电影，然后看看第一部相关的影评"

LLM 结果：✅

```
① searchInternet("2025年7月 热门电影") → 拿到电影列表+链接
② readUrl(第一部电影的影评链接) → 读影评内容
③ 生成回复
```

## 五、Skills 系统实现

### 核心设计

继承 Function Calling 的声明式抽象思路，将工具格式规则从 SYSTEM_PROMPT 拆分为独立 Skill 组件。

```
加载机制：
  用户消息 → invoke() 开始 → llm_think 第1轮
    → state.toolExecutionRequests 为空 → 不加 Skill
    → LLM 返回 tool_calls [queryWeather]

  llm_think 第2轮
    → SkillManager 读上轮 toolExecutionRequests
    → 发现 queryWeather → 加载 WeatherSkill
    → LLM 看到天气格式 + 组合规则

  invoke() 结束 → state 销毁 → Skill 自动卸载
```

Skill 接口定义在 `wechat-ai-common/.../skill/Skill.java`，不产生新依赖。

### 已实现的 4 个 Skill

| Skill | 绑定工具 | 规则 | 模块 |
|-------|---------|------|------|
| `WeatherSkill` | `queryWeather` | 🌤 天气格式 + 下雨/晴天景点推荐 | wechat-ai-tool |
| `DocumentSkill` | `searchDocument`, `getDocumentSummary` | 📄 文档检索格式 + 摘要格式 | wechat-ai-tool |
| `WebSearchSkill` | `readUrl`, `searchInternet` | 🔗 网页搜索与链接处理规则 | wechat-ai-tool |
| `ConversationSearchSkill` | `searchConversation` | 💬 历史对话搜索规则 | wechat-ai-tool |

### 保留在 SYSTEM_PROMPT 中的系统级规则

- 性格设定、工具清单描述
- 语音输出标记规则
- 未找到/错误回复格式
- 回复红线
- 图片消息处理规则

基础 Prompt 从 ~105 行精简到 ~70 行。

### 设计意图：为工具数量爆发做架构准备

Skills 系统的价值与工具数量正相关：

```
当前 6 个工具，关联性弱：
  queryWeather  → 无依赖
  searchInternet → 无依赖
  readUrl       → 无依赖
  searchDocument → 无依赖
  → 调用链价值 ≈ 0

后续加关联性工具时：
  sendEmail     → 需先搜收件人
  createEvent   → 需先解析时间
  uploadToCloud → 需先有文件
  → 调用链价值随关联度增长
```

当前拆的 4 个 Skill 只是验证机制走通。真正的收益在加 Email、日历、RAG 等强关联工具时才会显现——那时按工具组织的组合规则直接决定 LLM 能否准确完成多步任务。

## 六、待定：工具混合调用规范

当前各 Skill 的规则偏向"格式"，组合规则只有 WeatherSkill 的"天气+景点"。后续两个方向：
