## 1. 背景与问题

### 1.1 为什么 AI 需要"记忆"？

大语言模型本身是无状态的——它每次收到消息都像是"第一次见到你"。为了让 AI 能理解对话上下文，需要在每次请求时把历史消息也发给 LLM。

```
用户第1条："我叫小明"
  → LLM 看到 [system, user("我叫小明")]
  → 回复"你好小明！"

用户第2条："我叫什么名字？"
  → 如果没历史 → LLM 看到 [system, user("我叫什么名字？")]
  → 回复"你没说过你的名字" ❌
  → 如果有历史 → LLM 看到 [system, user("我叫小明"), assistant("你好小明！"), user("我叫什么名字？")]
  → 回复"你刚才说过啦，你叫小明！" ✅
```

**"记忆" = 把历史消息收集起来，每次请求时一起发给 LLM。**

### 1.2 记忆管理的三个维度

| 维度 | 说明 | 影响 |
|------|------|------|
| **持久性** | 进程重启后记忆是否还在 | 部署更新、崩溃恢复是否影响体验 |
| **容量** | 能记住多少轮对话 | 超过限制时怎么处理（截断/压缩） |
| **时效** | 记忆保留多久 | 过期的对话是否自动清理 |

## 2. 当前方案：内存记忆（v2.x 生产态）

### 2.1 架构

```
WechatServiceImpl
  │
  └─ Map<String, List<Map<String, Object>>> userContexts = new ConcurrentHashMap<>()
       │            ↑ userId      ↑ messageHistory
       │
       ├─ key:   "oWx_xxxxx"（用户 openid）
       │
       └─ value: [
       │           {role: "system",   content: "你是微信智能体助手..."},
       │           {role: "user",     content: "我叫小明"},
       │           {role: "assistant",content: "你好小明！"},
       │           {role: "user",     content: "南京天气如何？"},
       │           {role: "assistant",content: "今天南京......", tool_calls: [...]},
       │           {role: "tool",     content: "{"temperature": 33}"},
       │           {role: "assistant",content: "今天南京多云，33°C"}
       │         ]
```

### 2.2 运行流程

```
用户发消息
  │
  ├─ userContexts.get(fromUser) → 取出历史（或 null）
  │
  ├─ graph.invoke({ messageHistory: 历史 })
  │     │
  │     ├─ llm_think（追加当前消息 → 调 DeepSeek）
  │     ├─ tool_execute（如果需要）
  │     └─ llm_think → 回复
  │
  ├─ 取回更新后的 messageHistory
  │
  └─ userContexts.put(fromUser, 更新后的历史)
```

### 2.3 特性

| 特性 | 状态 | 说明 |
|------|------|------|
| 用户隔离 | ✅ | 按 userId 独立存储，多用户互不干扰 |
| 顺序保证 | ✅ | 同用户串行执行（独立线程池），消息不乱 |
| 消息完整 | ✅ | 完整保留 system/user/assistant/tool 全部角色 |
| 持久化 | ❌ | 进程重启 → ConcurrentHashMap 清空 → 失忆 |
| 容量控制 | ❌ | 无上限，消息越积越多直至超 token 限制 |
| 过期清理 | ❌ | 没有时间维度上的自动清理 |

### 2.4 重启失忆的具体影响

```
场景：线上部署新版，重启 Spring Boot
  重启前：
    userContexts = {
      "oWx_aaa": [system, user("合同内容"), assistant("已分析第3条...")],
      "oWx_bbb": [system, user("南京天气"), assistant("多云33°C")]
    }

  重启后：
    userContexts = {}  ← 全部丢失

  用户 oWx_aaa 继续发消息："那第5条呢？"
    → 内存里没有历史
    → LLM 只看到 [system, user("那第5条呢？")]
    → 回复："你没有提过第5条，请告诉我是什么合同" ❌
```

## 3. 目标方案：数据库持久化记忆

### 3.1 架构

```
┌─────────────────────────────────────────────────────────────────┐
│  WechatServiceImpl                                              │
│    └─ 收到消息 → 调 graph.invoke()                               │
│                            │                                     │
└────────────────────────────┼─────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│  chatGraph（完整图，已定义但暂未启用）                              │
│                                                                  │
│  START → session_prepare → prepare_input → llm_think            │
│                                              │                  │
│                                         tool_execute ←──────────┤
│                                              │                  │
│                                              └→ llm_think → END │
│                                                                  │
│  session_prepare 节点做的事：                                     │
│    1. 调 SessionService.getOrCreateActiveSession(userId)         │
│       → 查 MySQL session 表，自动创建或续期 24h                   │
│    2. 从 MySQL message 表加载最近 N 条消息                        │
│       → 放入 state，传给 llm_think                               │
│    3. llm_think 执行完毕后把新消息写回 message 表                  │
└─────────────────────────────────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│  MySQL                                                          │
│  ┌──────────────────┐   ┌──────────────────────┐                │
│  │  session 表       │   │  message 表           │                │
│  │                   │   │                      │                │
│  │  session_id (PK)  │←──│  session_id (FK)     │                │
│  │  user_id          │   │  role (USER/ASST/...) │                │
│  │  status           │   │  content (消息内容)    │                │
│  │  expire_at        │   │  tool_calls (JSON)    │                │
│  │  message_count    │   │  created_at           │                │
│  │  created_at       │   │                      │                │
│  └──────────────────┘   └──────────────────────┘                │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 SessionPrepareNode 职责

```java
// 伪代码：SessionPrepareNode.apply(state)
public State apply(State state) {
    String userId = state.getUserId();

    // 1. 获取或创建活跃会话（MySQL 自动比较 expire_at）
    SessionEntity session = sessionService.getOrCreateActiveSession(userId);

    // 2. 从 message 表加载最近历史（例如最近 50 条）
    List<MessageEntity> messages = messageMapper
        .findLatestBySessionId(session.getSessionId(), 50);

    // 3. 组装 messageHistory，放入 state
    state.put("sessionId", session.getSessionId());
    state.put("messageHistory", messages);

    return state;
}
```

### 3.3 消息持久化流程

```
用户发消息
  │
  ├─ session_prepare
  │     ├─ getOrCreateActiveSession → 获取/创建 sessionId
  │     └─ 从 message 表加载历史
  │
  ├─ llm_think（调 DeepSeek）
  │     ├─ 同时向 message 表 INSERT 一条 {role: USER, content: 用户消息, session_id: ...}
  │     └─ 收到回复后 INSERT {role: ASSISTANT, content: 回复, session_id: ...}
  │
  ├─ tool_execute（如果需要）
  │     └─ INSERT {role: TOOL, ...} / 更新 assistant 记录的 tool_calls 字段
  │
  └─ 回复用户
```

### 3.4 各个边界的处理策略

#### 容量控制

| 策略 | 实现方式 | 适用阶段 |
|------|---------|---------|
| **消息轮数截断** | 只取最近 N 条（如 50 条），超出丢弃最早 | 初期 |
| **Token 计数截断** | 计算总 token 数，接近上限时丢弃最早消息 | 中期 |
| **历史摘要压缩** | 将早期消息压缩为一段摘要保留 | 后期（LLM 调用成本高） |

初期直接按轮数截断即可，不需要计算 token：

```sql
-- 取最近 50 条消息
SELECT * FROM message
WHERE session_id = ?
ORDER BY created_at DESC
LIMIT 50;
```

#### 过期清理

session 表已经有 `expire_at` 字段，由 `getOrCreateActiveSession()` 维护：

```
用户发消息 → getOrCreateActiveSession()
  ├─ 有活跃 session → 续期 24h（UPDATE expire_at = NOW() + 24h）
  └─ 无活跃 session → 创建新 session（expire_at = NOW() + 24h）
```

过期的 session 和 message 通过定时任务（每日凌晨）物理清理：

```sql
-- 清理过期 session 及其消息
DELETE m FROM message m
JOIN session s ON m.session_id = s.session_id
WHERE s.expire_at < NOW() - INTERVAL 7 DAY;
```

#### 和当前内存方案的差异

| 场景 | 当前内存方案 | 数据库持久化方案 |
|------|------------|----------------|
| 项目重启部署 | ❌ 失忆 | ✅ 恢复 |
| 消息超长 | ❌ 越积越多 | ✅ 限制最近 N 条 |
| 跨 24h 对话 | ❌ 一直累积 | ✅ 自动新 session |
| 管理后查看记录 | ❌ 无法查看 | ✅ 直接查 message 表 |

## 4. 迁移计划

### 阶段一：启用 chatGraph（约 10 分钟）

```
改动文件：
  wechat-ai-ai/.../config/ChatGraphConfig.java
    → 取消 chatGraph() 方法的注释
    → 确保 SessionPrepareNode 的依赖注入正确

  wechat-ai-ai/.../node/SessionPrepareNode.java
    → 确认 sessionService.getOrCreateActiveSession() 调用正确
    → 确认 messageMapper.findLatestBySessionId() 存在

  wechat-ai-wechat/.../WechatServiceImpl.java
    → callAiEngine() 不再需要手动传递 messageHistory
    → 去掉 ConcurrentHashMap userContexts 及相关代码
```

效果：AI 对话切换到 MySQL 持久化消息，ConcurrentHashMap 退役。

### 阶段二：容量控制

```
  messageMapper.findLatestBySessionId()
    → 加上 LIMIT 限制（默认 50 条）

  llm_think 处理后：
    → 新消息写回 message 表
```

### 阶段三：定时清理（可选，线上部署后）

```
  新增定时任务（@Scheduled）：
    每天凌晨 3:00 清理 expire_at < NOW() 的 session 及关联 message
```

## 5. 两种方案对比总览

| 对比项 | 内存方案（当前） | 数据库方案（目标） |
|--------|---------------|-----------------|
| 存储位置 | `ConcurrentHashMap` | MySQL message 表 |
| 持久性 | 进程重启丢失 | 永久保存 |
| 容量控制 | 无 | 最近 N 条截断 |
| 过期机制 | 无 | session 24h 自动过期 |
| 消息可追溯 | ❌ 无法查历史 | ✅ 可 SQL 查询 |
| 实现复杂度 | 低（~20 行） | 中（~80 行 + 1 个节点） |
| 启用前提 | 无需数据库 | 需要 MySQL 连接正常 |
| 对 LLM 调用量影响 | 无 | 无差别（同样传历史给 LLM） |

## 6. FAQ

### Q: 为什么第一期不直接用数据库方案？

因为项目初期 `ConcurrentHashMap` 够用，且不依赖 MySQL（纯对话功能不需要数据库）。减少前期配置负担，让组员能先跑起来验证全链路。

### Q: 迁移后用户会察觉区别吗？

正常情况下不会。唯一区别是项目重启后用户发现 AI 还记得之前聊了什么——这是体验提升不是退化。

### Q: 消息存 MySQL 会不会太慢？

每次请求读最近 50 条消息，MySQL 走 `session_id` 索引 + `LIMIT` 截断，单次查询在毫秒级，对整体响应时间无影响。如果后期数据量大可以加 Redis 缓存热消息。

### Q: 切换后并发 HashMap 的代码怎么处理？

直接删除 `userContexts` 字段及相关代码即可。多用户隔离由 session 表的 `user_id` + `session_id` 保证，比内存 Map 更可靠。
