## 二、工具池扩容方案

### 对标 OpenClaw

分析了 OpenClaw 的工具体系（20+ 消息平台、10+ 核心能力、社区 TOP 10 Skills），结合微信助手当前的 8 个工具，制定分三批扩容到 20 个的方案：

| 批次 | 工具数 | 工具 | 外部依赖 | 预计工期 |
|:----:|:------:|------|---------|:-------:|
| P0 | 4 | calculate, **translate** ✅, queryNews, queryDictionary | 百度翻译 API（已注册） | 2 天 |
| P1 | 4 | queryStock, queryExpress, queryIpLocation, createNote | 快递100/聚合数据/MySQL | 2 天 |
| P2 | 4 | generateImage, sendEmail, queryCalendar, weatherAlert | DashScope/Spring Mail | 2-3 天 |

每个工具都带有完整的 Java 伪代码、Skill 映射、配置项和测试用例，写入 `工具池扩容方案-8to20.md`。

### 核心设计思路

- **@Tool description** 管"调不调工具"（触发条件）
- **Skill prompt** 管"调用后怎么处理"（格式+组合规则）
- 旧 tool description 太弱→LLM 不触发工具直接用自己的能力回；新方案加了 **"不得使用自身语言能力直接回复翻译结果"** 的强制规则
- 唯一新增 Maven 依赖：`spring-boot-starter-mail`（P2 sendEmail 用）

## 四、generateDocument 文档生成工具

### 需求

用户让 AI "写一份租房合同/工作总结" → LLM 生成内容 → 存 MySQL 可搜索 + 写本地文件 → 微信自动发送文件给用户。

### 架构

沿用 TTS 语音输出的 `[VOICE]` 标记模式，新增 `[FILE:path]` 标记：

```
用户说"帮我写一份租房合同，保存为docx"
  → LLM 生成合同内容
  → 调 generateDocument
  → GenerateDocumentTool:
      ① DocumentService.createTextDocument() → MySQL (status=PARSED)
      ② 按文件名后缀选格式：
           .txt  → Files.writeString()
           .docx → XWPFDocument 排版（标题加粗居中+正文宋体缩进）
      ③ 返回路径 + [FILE:path] 标记
  → LLM 回复末尾带 [FILE:D:/wechat_files/.../文件.txt]
  → WechatOutboundSender 检测到 [FILE:]
  → 读取本地文件 → iLink sendFile → 用户微信收到文件
```

### 涉及的组件

| 组件 | 改动 | 说明 |
|------|------|------|
| `GenerateDocumentTool` | 新增 | @Tool 工具，文件名含 `.docx` 则生成 Word |
| `DocumentGenSkill` | 新增 | 文档生成规则 |
| `DocumentService` | 新增 `createTextDocument()` | 跳过上传解析，直接写库 |
| `WechatOutboundSender` | 新增 `[FILE:]` 检测 | 与 `[VOICE]` 完全对称的可扩展标记机制 |

### 踩坑记录

| # | 问题 | 解决 |
|---|------|------|
| 1 | `.properties` 中 `D:\wechat_files\generated` 反斜杠被吞（`\w` 被当转义） | 所有路径用正斜杠 `/` |
| 2 | 路径含中文经过 LLM 响应后乱码 | 存储路径改用纯英文 `D:/wechat_files/` |
| 3 | 工具生成文件后如何让微信发送 | 复用 `[VOICE]` 标记模式，加 `[FILE:path]` 标记 |

### 验证

```
用户："帮我写一份租房合同"
→ 工具返回路径 → LLM 回复带 [FILE:path] → 微信收到文件 ✅
→ 同时写入 document 表 → 可 searchDocument 搜索 ✅

用户："帮我写一份租房合同，保存为docx"
→ 文件名含 .docx → 生成 Word 文档 → 微信收到 .docx ✅
```

## 五、发送邮件工具

### 技术方案

Spring Boot `JavaMailSender` + QQ 邮箱 SMTP，零新代码模式，仅配置即可。

### 关键实现

| 项目 | 说明 |
|------|------|
| 工具类 | `SendEmailTool.java` — @Tool，注入 JavaMailSender 直接发送 |
| 配置 | `spring.mail.host=smtp.qq.com`，端口 587，STARTTLS |
| 确认机制 | EmailSkill 约束：发送前向用户完整展示收件人/主题/内容，问"确认吗？" |
| 安全 | `helper.setFrom(fromAddress)` 确保发件人与认证账号一致 |

### 踩坑

| # | 问题 | 解决 |
|---|------|------|
| 1 | 报 `501 Mail from address must be same as authorization user` | 加 `helper.setFrom(spring.mail.username)` |
| 2 | `MailSendException` 不是 `MessagingException`，catch 不住 | 同时 catch `MailException \| MessagingException` |
| 3 | 自然语言确认依赖 LLM 自律 | 后续通过图中断机制提供系统级保障 |

### 验证

```
用户："发邮件给 1021839926@qq.com 说测试"
→ LLM 确认："收件人：... 主题：... 内容：... 确认发送吗？"
→ 用户："没问题"
→ LLM 调 sendEmail → "✅ 邮件已发送" ✅
```

## 六、LangGraph 图中断机制设计

### 背景

当前 WRITE 工具的确认机制依赖 Skill 规则约束 LLM，属于"自律"而非"系统强制"。

### 方案

利用 LangGraph4j 1.8.18 的 `interruptBefore` + `MemorySaver` 机制，在 `tool_execute` 节点前中断图，等待用户确认后再恢复：

```
→ llm_think 返回 tool_calls → 路由到 tool_execute
→ ⛔ interruptBefore("tool_execute") — 中断！
→ MemorySaver 保存 checkpoint
→ 检查工具列表：有 WRITE → 挂起问用户确认
→ 用户确认 → invoke(null) 恢复
→ 用户取消 → 丢弃 checkpoint
```

### 设计文档

详见 `LangGraph图中断机制设计.md`（12 章 + 4 附录，含反编译 API 分析、完整代码、实施计划）
