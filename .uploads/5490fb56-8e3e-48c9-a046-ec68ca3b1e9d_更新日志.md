- 前端会话列表仍在 localStorage；库中可按 `user_id` 查到桌面会话

## v2.27（2026-07-31）

### 行为路径自学习系统（Phase 1-3）

一个基于 RAG 的自我进化系统。每次 Agent 的工具调用链作为"行为路径"存入向量库，新事件来时通过 embedding 相似度检索召回历史相似任务，按贝叶斯置信度排序复用。用户反馈作为监督信号更新置信度，失败时由独立 Critic LLM 分析原因生成规则。

**新建模块**：`wechat-ai-proactive`（第 9 个 Maven 子模块），依赖 common/session/document/tool/agent。

#### Phase 1 — 核心闭环

`BehaviorPathService` 三个入口方法：
1. `retrieveAndDecide()` — Agent 启动前：userMessage → Embedding → Qdrant 向量检索 → 策略决策（fast/hybrid/slow）
2. `recordAfterAgent()` — Agent 完成后：录制工具链 → 写入 MySQL + 索引到 Qdrant
3. `collectFeedback()` — 下条消息到来时：解析用户反馈 → 更新 Beta 分布置信度（α/β）

反馈解析器（`FeedbackParser`）基于正则词库，区分强正面/温和正面/强负面/温和负面/中性。

集成点（纯增量）：`AgentGraphRunner.run()` 开头调 retrieveAndDecide + 结尾调 recordAfterAgent；`WechatChatBridge.doThink()` 开头调 collectFeedback。

新增 3 张 MySQL 表：`behavior_paths` / `decision_traces` / `path_evaluations`。Qdrant 独立 collection `behavior_paths`，复用现有 `EmbeddingService`（DashScope text-embedding-v3）。

#### Phase 2 — Critic 反思

- `CriticTriggerDecider`：failure/harmful/ignored/partial → 必触发；success+新路径 → 触发一次
- `CriticEvaluator`：调 DeepSeek 分析失败（三元组：事件 + Agent动作 + 用户反应），返回结构化 `CriticVerdict`（score/verdict/root_cause/learned_rule）
- 规则绑定到路径的 `critic_rules` JSON 列，**RAG 命中该路径时才注入**（不是全局注入）
- 时间衰减因子：7天内 1.0 / 30天 0.8 / 90天 0.5 / 超过 0.2

#### Phase 3 — 路径库维护

- `PathMergeService`：启动时全量扫描，sim>0.85 + 同 tool_chain → 合并 α/β，保留最早路径
- `PathMaintenanceScheduler`：
  - 每天凌晨 3 点归档过期路径（90天未用 + use_count<10）
  - 每天凌晨 4 点检测矛盾路径（fail≥3 且 success≥3 → 标记 degraded）
- 个人权重：用户使用同一路径 3 次以上，finalConf = 0.7×全局 + 0.3×个人
- degraded 路径强制走温路径，不升级热

#### 配置新增

```properties
wechat.proactive.enabled=true
wechat.proactive.hot-threshold=0.75
wechat.proactive.min-similarity=0.6
wechat.proactive.retrieve-top-k=10
wechat.proactive.qdrant.collection=behavior_paths
```

#### 数据库变更

```sql
ALTER TABLE behavior_paths ADD COLUMN critic_rules JSON;
ALTER TABLE behavior_paths MODIFY COLUMN outcome 
  ENUM('success','partial','failure','ignored','harmful','degraded') NOT NULL;
ALTER TABLE decision_traces MODIFY COLUMN outcome 
  ENUM('success','partial','failure','ignored','harmful') NOT NULL DEFAULT 'partial';
ALTER TABLE path_evaluations MODIFY COLUMN user_reaction_type 
  ENUM('explicit_positive','explicit_negative','implicit_positive',
       'implicit_negative','neutral','none','other');
```

#### 模块结构

```
wechat-ai-proactive/src/main/java/com/wechatai/proactive/
├── config/ProactiveConfig.java
├── model/{BehaviorPath,DecisionTrace,PathEvaluation,FeedbackSignal}
├── path/{BehaviorPathService,ConfidenceUpdater,PathEmbeddingService,
│        BehaviorPathMapper,PathMergeService,PathMaintenanceScheduler}
├── feedback/FeedbackParser.java
└── critic/{CriticTriggerDecider,CriticEvaluator,CriticVerdict,RuleInjector}
```

## v2.26（2026-07-28）

### ReAct 超时看门狗

三层超时保护，解决工具卡死导致用户线程永久阻塞：

- **工具级**（wechat.watchdog.tool-timeout-ms，默认 60s）：ToolExecuteNode 三个执行路径各包 `CompletableFuture.orTimeout()`，超时注入 error JSON 让 LLM 换策略，消息序列完整不会 400
- **Agent 级**（timeoutMs 参数，默认 30s）：AgentGraphRunner.run() 内 invoke+resume 循环包 `Future.get(timeoutMs)`，超时返回 AgentResult.fail
- **Bridge 总超时**（wechat.watchdog.bridge-timeout-ms，默认 120s）：doThink() 包总超时壳，超时发提示给用户并释放线程

新增 `RunWatchdog.java`（Cached 线程池 + 两个 runWithTimeout 重载），配置可在 application.properties 修改。

### 猎聘 MCP 接入

接入猎聘官方 MCP 服务（`open-agent.liepin.com/mcp/user`），13 个求职工具：

- 简历查询/编辑：`my-resume` + 4 个 add + 6 个 modify
- 求职操作：`user-search-job`（按经验/学历/公司性质/地点/薪资/关键词搜职位）、`user-apply-job`（传 jobId 一键投递）

新增 `LiepinMcpSource.java`（JSON-RPC 2.0 over HTTP，x-user-token 认证）、`LiepinMcpConfigProperties.java`。`user-apply-job` 标记 WRITE，走图中断确认。

相比浏览器自动化：无验证码、无填表错误、无反爬风险、API 调用 170ms。

### Agent 工具分配优化

- `AgentToolRegistry` 新增 `getLiepinTools()`、`getGeneralToolsWithLiepin()`

### jobAgent 独立拆分

猎聘工具从 generalAgent 拆出为独立 `jobAgent`（`AGENT:Job`），和 taxiAgent 同级。新增 `JOB_AGENT_PROMPT`（API 优先、原样输出、系统确认）。Agent 体系现为 4 个：generalAgent / taxiAgent / filesystemAgent / jobAgent。

### MCP 包结构整理

`mcp/` 9 文件平铺 → 拆三层：`mcp/`（接口/POJO/通用）、`mcp/impl/`（实现）、`mcp/config/`（配置）。

### OkHttp 超时修复

DeepSeek 冷启动/大响应超 okhttp 默认 10s 读超时 → 最终方案：`LlmService.init()` 改用 JDK `HttpClient`（connect 30s / read 120s），零废弃 API。

`LlmService` 内置熔断器，三重触发条件任一拉闸：连续 3 次 400 | 连续 8 次异常 | 单次消息超 150 条。拉闸后所有 LLM 请求直接返回"已熔断，请重启"，不再烧 API 额度。仅重启可恢复。

### 双向清理增强 + 消息上限

`cleanupOrphanedToolCalls` 重写：Pass 1 收集合法 tool_call_id → Pass 2 双向清理（孤儿 assistant(tc) + 孤儿 tool）→ Pass 3 连续 assistant 去重。MAX_ROUNDS 从 150 → 30（最多 60 条非系统消息）。

### 实验性改动

#### 1. 消息丢失排查

**涉及文件**：
- `wechat-ai-wechat/.../WechatConnectionManager.java`

**问题**：用户连续发送多条消息时，部分消息无日志无回复地丢失。经全链路日志追踪后确认**根因为 iLink SDK 长轮询竞态条件**：

```
POLL#6 getUpdates → 0 条 (18091ms)    ← 长轮询超时
                    ↓ 用户在这期间发了第一张图
POLL#7 getUpdates → 1 条 (items=[2])  ← 只拉到了第二张图
POLL#8 getUpdates → 1 条 (items=[2])  ← 只拉到了第三张图（第一张丢了）
```

长轮询超时瞬间，服务端游标已推进但客户端没收到消息，后续轮询用新游标已跳过。

**结论**：SDK 协议层设计局限，无 WebSocket 推送、无按 ID 补拉接口，当前无根治方案。

**有效优化**：
- 纯文本场景在加 `continue` 快速拉取后改善明显
- `readTimeoutMs` 从默认 ~18s 调整为 **15s**（代码已回退默认值后确认方向无效，保留 15s 减少超时日志频率）
- getUpdates 超时日志改为 warn，不再打印堆栈

#### 3. 语音触发词补充

**涉及文件**：
- `wechat-ai-ai/.../ai/LlmService.java`

**改动**：语音输出规则的触发词从 3 个扩展为：
- 原：说给我听、语音回复、用嘴说
- 现：读给我听、读出来、读一下、念给我听、说给我听、用嘴说、语音回复、语音说、讲出来、用说的

同时加了总则 `当用户要求用语音/口头朗读内容时`，覆盖未列出的同义表达。

验证：`帮我查一下2024巴黎奥运会中国金牌，然后读给我听` → 成功触发 `[VOICE]` ✅

#### 2. 对话消息 MySQL 持久化

**涉及文件**：

**目标**：从内存方案（ConcurrentHashMap）升级为 MySQL 持久化，重启不丢失

**架构**（缓存优先策略）：

```
正常对话（缓存命中）：
  WechatServiceImpl → userContexts(ConcurrentHashMap) → 传入图
    → SessionPrepareNode 检测到已有 messageHistory → 跳过查库
    → LlmService 调 LLM → 同时写 MySQL(user + assistant)
    → ToolExecuteNode 执行工具 → 同时写 MySQL(tool 结果)

重启后（缓存未命中）：
  userContexts 空 → SessionPrepareNode 从 MySQL 加载最近 50 条
    → 后续流程同上
```

**关键设计**：

| 决策 | 说明 |
|------|------|
| 缓存优先 | 有内存缓存就不查 MySQL，性能不受影响 |
| `ORDER BY id DESC` | 用自增主键排序保证消息顺序，不用 `created_at`（同一秒内乱序） |
| System Prompt 不存 DB | 只在消息列表第一条动态注入，DB 中只存 user/assistant/tool 消息 |
| 50 条上限 | 限制加载条数，避免长对话上下文膨胀 |
| `tool_call_id` 恢复 | 从 MySQL 加载 tool 消息时从 toolCalls JSON 中提取 `tool_call_id` 字段 |

**图结构变更**：

```
改前（simpleChatGraph）：
  START → prepare_input → llm_think → [tool_execute]

改后（simpleChatGraph + session_prepare）：
  START → prepare_input → session_prepare → llm_think → [tool_execute]
```

**清理旧代码**：删除了 ChatGraphConfig 中注释掉的 60 行旧 `chatGraph` 方法，以及未使用的 `ChatLanguageModel` 导入。

### 当前文件处理流程

```
微信发文件 → handleFileMessage
  → client.downloadFileFromMessageItem() → byte[]
  → sessionService.getOrCreateActiveSession() → sessionId
  → documentService.upload(userId, sessionId, fileName, fileBytes)
      ├─ 校验文件类型（pdf/doc/docx/txt）
      ├─ 校验大小（≤ 50MB）
      ├─ 保存到 D:\解析文件\upload\yyyy-MM-dd\f_xxx.ext
      ├─ 写 MySQL（status=UPLOADED）
      ├─ 选解析器 → 同步解析（PDFBox / POI / TXT）
      ├─ 写 MySQL（status=PARSED, content=文本）
      └─ 返回 DocumentVO
  → callAiEngine → LLM 回复用户"已收到并完成解析"

用户提问"合同里违约条款怎么写？"
  → callAiEngine
  → LLM 选 searchDocument → SearchDocumentTool
  → DocumentService.search(keywords, fileIds, maxResults, sessionId)
  → MySQL FULLTEXT（MATCH…AGAINST）+ LIKE 兜底 → 返回匹配段落
  → LLM 组织回答 → 回复用户
```

### ngram 中文分词

**涉及文件**：MySQL 数据库（INDEX 定义）

**改动内容**：

| 改动 | 说明 |
|------|------|
| 新增 `WITH PARSER ngram` | 将 document 表的 FULLTEXT 索引改为 ngram 中文分词器，支持中文关键词搜索 |

**原因**：MySQL 默认 FULLTEXT 分词器按空格分词，中文没有空格，导致"试用期 劳动合同"等中文搜索无法命中。ngram 按每 2 字一组切词，适合中文场景。

**验证**：发送"我刚入职，试用期工资70%合法吗" → `searchDocument` 搜索命中 `劳动合同法` 相关条款 ✅

**执行 SQL**：
```sql
ALTER TABLE document DROP INDEX ft_content;
ALTER TABLE document ADD FULLTEXT INDEX ft_content (content) WITH PARSER ngram;
```

**涉及文件**：`wechat-ai-document/.../service/DocumentServiceImpl.java`

### 二、ToolRegistryImpl 完整实现

从空实现（返回 `Collections.emptyList()`）改为完整的 `@Tool` 扫描注册机制。

#### 2.1 扫描流程

```
Spring 容器启动 → new ToolRegistryImpl(ApplicationContext)
                                   │
                      getEnabledToolBeans() / listTools() 第一次被调用时
                                   │
                 懒扫描所有 Bean（@Component 已注册完毕，无循环问题）
                                   │
                 逐个检查每个 Bean 的方法 → 找到 @Tool 注解 → 注册
```

#### 2.2 功能表

| 功能 | 实现方式 |
|------|----------|
| 工具发现 | 遍历 `ApplicationContext.getBeanDefinitionNames()`，检查每个 Bean 的 `Method` 上是否有 `@Tool` 注解 |
| 参数推导 | 根据 `Method.getParameters()` 的类型自动生成 JSON Schema：`String → string`，`int/Integer → integer`，`List → array` 等 |
| 描述提取 | `@Tool("...")` 的 value 作为工具描述，`@P("...")` 的 value 作为参数描述 |
| 启用状态 | 每个工具有 `enabled` 字段，支持运行时 `toggle(name, true/false)` 启停 |
| 懒初始化 | 使用 `volatile boolean scanned` + `synchronized` 保证首次调用时扫描一次，避免 `@PostConstruct` 时与 `ApplicationContext` 循环引用 |

#### 2.3 命名规则与冲突

- 工具名 = `@Tool` 方法的方法名（camelCase）
- 同名冲突先注册的保留，后注册的打 `WARN` 日志跳过
- 目前注册的 3 个工具：`getDocumentSummary`、`queryWeather`、`searchDocument`

#### 2.4 循环依赖处理

**问题**：`ToolRegistryImpl` 注入 `ApplicationContext` 扫描全部 Bean，Spring 检测到与 `ToolController` → `ToolRegistry` 的间接循环。
**解决**：不在 `@PostConstruct` 中扫描，改为**懒扫描**（第一次被调用时再扫描），此时所有 Bean 已创建完毕。

### 三、LLM 引擎设计

#### 3.1 方案选型（两阶段对比）

| 阶段 | 方案 | 结果 | 原因 |
|------|------|------|------|
| 初版（已废弃） | LangChain4j `OpenAiChatModel` | ❌ 运行时异常 | 与 `langchain4j 1.0.0-beta1` 的 OpenAi 模块兼容性不佳 |

#### 3.2 架构

```

  │
  ├─ @Value("${wechat.ai.llm.api-key}")      → API Key
  ├─ @Value("${wechat.ai.llm.base-url}")      → API URL
  ├─ @Value("${wechat.ai.llm.model}")         → 模型名
  ├─ RestClient.Builder (Spring 自动注入)      → HTTP 客户端
  └─ ToolRegistry (@Lazy 注入，避免循环依赖)    → 工具清单
```

#### 3.3 请求格式（OpenAI 兼容）

```json
{
  "model": "deepseek-chat",
  "messages": [
    {"role": "system", "content": "你是微信智能体助手..."},
    {"role": "user", "content": "查询一下南京的天气"}
  ],
  "tools": [{"type": "function", "function": {
    "name": "queryWeather",
    "description": "查询指定城市的实时天气...",
    "parameters": {
      "type": "object",
      "properties": {"city": {"type": "string", "description": "城市名称..."}},
      "required": ["city"]
    }
  }}],
  "temperature": 0.7
}
```

#### 3.4 消息历史维护（ReAct 循环）

```
首轮 (llm_think):
  messages = [system, user("北京天气")]
                                              → DeepSeek 返回 tool_calls
  → LlmService 把 assistant(tool_calls) 追加到 messages
  → messages = [system, user, assistant(tool_calls)]
  → 返回 {messageHistory, toolExecutionRequests, needTool: true}

次轮 (tool_execute):
  ToolExecuteNode 收到 toolExecutionRequests
  → 反射调用 QueryWeatherTool.queryWeather("Beijing")
  → tool(result) 追加到 messages
  → messages = [system, user, assistant(tool_calls), tool(结果)]
  → 返回 {messageHistory, needTool: false}

三轮 (llm_think 再次):
  读取完整 messages → DeepSeek 看到工具结果
  → 返回"北京多云，26°C"
  → messages = [..., assistant("北京多云，26°C")]
  → 返回 {reply: "北京多云...", needTool: false}
  → END
```

### 四、ToolExecuteNode 实现

#### 4.1 执行流程

```
ToolExecuteNode.apply(state)
  │
  ├─ ① 从 state.data() 读取 toolExecutionRequests (List<Map>)
  │     每项包含: {id, type, function: {name, arguments}}
  │
  ├─ ② 遍历每个 tool call：
  │     ├─ 根据 function.name 查找对应的 @Tool Bean
  │     │   （遍历 getEnabledToolBeans()，方法名匹配 @Tool 注解）
  │     ├─ 用 Jackson 解析 arguments (JSON String → Map)
  │     ├─ 按方法参数顺序做类型转换（String/Integer/List 等）
  │     ├─ 反射调用：method.invoke(bean, paramValues)
  │     ├─ 结果序列化为 JSON String
  │     └─ 追加到 messageHistory：{role: "tool", tool_call_id, content}
  │
  └─ ③ 返回 {messageHistory, needTool: false}
```

#### 4.2 错误处理

| 异常场景 | 行为 |
|----------|------|
| 未找到对应 Bean | 结果中写 `{"error": "未找到工具: xxx"}` |
| 参数解析失败 | Jackson 抛异常，结果中写错误信息 |
| 工具方法内部抛异常 | 由工具自身的异常处理接管，向上传播 |

```
  │     ├─ prepare_input（占位）
  │     ├─ llm_think → DeepSeek → tool_calls
  │     ├─ tool_execute → QueryWeatherTool → 结果回填
  │     └─ llm_think → DeepSeek → 回复文本
  │
  ├─ client.sendText(fromUser, reply)
  │
  └─ 用户看到"南京市今天阴，33°C..."
```

#### 6.2 关键设计

- **同步处理**：iLink 无 5 秒超时限制（不同于微信公众号），直接同步等图执行完再回复
- **提示消息**：先发"已收到，正在思考..."给用户，AI 处理完成后发真正回复
- **错误兜底**：图执行异常时发"抱歉，处理出错了，请稍后再试"

## v1.2（2026-07-16）

### 对团队的影响
- 传统 Java 组员写工具的方式不变（仍然是 `@Component` + `@Tool`），不再需要写 HTTP 接口
- 会话模块不需要对外暴露创建接口，内部自动管理
- 列表接口返回直接数组，前端不需要解析分页结构

### 设计思路：ReAct 循环编排
AI 引擎采用 **ReAct 模式（Reasoning + Acting 循环）** 作为核心编排逻辑，而非串行多节点路由：

```
LLM 思考 → 需要工具？→ 执行工具 → 结果回填 → 继续循环
                ↓
          不需要了 → 回复用户 → 结束
```

**优点**：
- 无需手动枚举意图路径（查→发、发→查、只查、只发……），LLM 看图里的工具清单自行组合
- 多轮工具调用由循环边自动处理，工具越多收益越大
- 所有工具调用历史由 LangGraph State 自动累积，LLM 每次看到完整上下文

**原因**：微信用户不需要手动创建会话。会话改为由 `SessionService.getOrCreateActiveSession()` 内部自动管理：有活跃会话就续期 24h，没有就自动创建。

| 变更 | 说明 |
|------|------|

| `ToolCallbackReq` 删除 | 不再需要外部工具回调 |
| `PageReq` / `PageResp` 删除 | 第一期不做分页 |
| `ToolExecuteReq/Resp` | 改为内部 DTO，不再通过 HTTP |

**原因**：PDFBox / POI 不提供进度回调，算进度需要预扫描文件，耗时等同解析本身，得不偿失。且调用方只看状态（`PARSED` / `PARSING` / `FAILED`）就够了，`parseProgress` 无实际消费方。

**原因**：团队偏好统一使用 `.properties` 而非 `.yml`。

### 7. 接入方式更灵活（公众号 / 机器人 SDK 均可）
**原因**：不限定只能用微信公众号，后续可能接入微信机器人（如 Wechaty）。接入层只负责消息收发，适配不同 SDK 时替换 wechat 模块内部实现即可，对外接口不变。

## v2.8（2026-07-20）

### 修复：消息间歇性丢失（仍有概率触发）

**涉及文件**：
- `wechat-ai-wechat/.../WechatConnectionManager.java`
- `wechat-ai-wechat/.../WechatInboundHandler.java`

**问题**：用户连续发送多条消息时，部分消息无日志无回复地丢失。

**排查过程与尝试修复**：

| 尝试 | 改动 | 结果 |
|------|------|:----:|
| `continue` 无间隔轮询 | 有消息时跳过 sleep，立即拉下一批 | 纯文本改善，图片+文本仍概率丢 |
| 轮询间隔 1s → 100ms | 无消息时 sleep(100) | 无明显改善 |
| 去掉 `continue`，固定 100ms | 始终 sleep(100)，不再无间隔调 SDK | 仍概率丢 |
| `handleImage` 异步化 | 下载+识别移到用户线程池，不阻塞轮询线程 | 纯优化，不解决丢消息 |

**当前状态**：根因未找到，推测为 iLink SDK 或微信服务端消息投递机制问题。加入日志追踪。

### 修复：SessionPrepareNode 内存/DB 消息数不一致

**涉及文件**：
- `wechat-ai-ai/.../node/SessionPrepareNode.java`
- `wechat-ai-ai/.../ai/LlmService.java`

**问题**：`SessionPrepareNode` 的 `HISTORY_LIMIT = 50`，但 `LlmService` 消息上限为 150 轮（300 条非 system 消息）。DB 消息超过 50 条后，从 MySQL 加载最近 50 条时可能切在 `assistant(tool_calls)` / `tool(result)` 中间，导致 DeepSeek 报 `tool must follow tool_calls`。

**修复**：

1. `SessionPrepareNode.java`：`HISTORY_LIMIT` 从 **50 → 300**，与 LlmService 的 150 轮保持一致
2. `SessionPrepareNode.java`：从 MySQL 加载后检查第一条是否为 `user`，不是则裁到第一个 `user`，彻底是残片则返回空列表让 LlmService 重新开始
3. `LlmService.java`：截断后同样做链完整性检查

### 多机器人集群（设计思路）

**背景**：当前单微信号在所有用户之间共享，受微信风控（频率限制）和单设备登录限制。

**目标方案**：启动时生成 N 个独立的 iLink 客户端，每人一个专属机器人号。

```
启动时分配 4 个 ILinkClient
  ├── Bot1 → 线程1 轮询 → 服务用户组A
  ├── Bot2 → 线程2 轮询 → 服务用户组B
  ├── Bot3 → 线程3 轮询 → 服务用户组C
  └── Bot4 → 线程4 轮询 → 服务用户组D

按 userId hash 或扫码时绑定固定用户路由
```

**改动范围**：

| 文件 | 改动 |
|------|------|
| `application.properties` | 加账号列表配置（`wechat.bot.accounts[0].id` 等） |

| 路由层 | 新增 `BotRouter`，按 userId 分配到对应 Bot |

**前提条件**：
- 需要 N 个可登录的微信号（每个需独立手机号）
- 注意同一 IP 多号的风控风险

**当前不做原因**：单机器人 + session 隔离已满足使用，多机器人运维成本高。详见 `devlog-2026-07-20.md`。

## v2.28（2026-07-29）

### RAG 文档语义检索

将文档检索从「LLM 工具调用模式」改造为「RAG 预处理模式」，用户发消息时自动从 Qdrant 向量库检索相关文档 chunk，注入 system prompt，LLM 无需手动调用 `searchDocument`。

**核心变更**：

- **Qdrant 向量库接入**：云端实例，1024 维 Cosine 相似度，sessionId 过滤实现会话级隔离
- **Embedding 模型**：阿里云 DashScope `text-embedding-v3`（1024 维），原生 API 调用
- **文档切块**：段落感知分块，500 字/chunk，50 字重叠
- **检索策略**：每轮 `llm_think` 自动 embed 用户消息 → Qdrant 搜索 topK=5/minScore=0.5 → 拼入 system prompt
- **改图方案 C**：RAG 检索嵌入 `LlmService.think()`，在 `skillManager.enrich()` 之前执行。图拓扑不变

**新增文件**：
