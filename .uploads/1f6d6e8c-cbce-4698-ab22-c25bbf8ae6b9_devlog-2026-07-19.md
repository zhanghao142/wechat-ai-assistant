## 概述

今天实现了文件解析功能的完整链路。从 PDFBox/POI/TXT 三个解析器，到 MySQL FULLTEXT 搜索，到微信收文件消息后的下载→上传→同步解析→回复，全链路跑通。同时补齐了会话模块的 `getOrCreateActiveSession` 实现、数据库环境搭建、配置文件适配。

**关键决定**：放弃异步队列方案，上传时**同步解析**。因为第一期数据量小，同步解析简单可靠，用户上传后立刻能搜。

## 二、今日开发内容

### 2.1 三个解析器（PDFBox / POI / TXT）

**涉及文件**: `PdfParser.java`、`WordParser.java`、`TxtParser.java`

三个解析器都实现了 `DocumentParser` 接口：

```java
public interface DocumentParser {
    boolean supports(FileType fileType);
    String parse(InputStream inputStream) throws Exception;
}
```

**PdfParser** — Apache PDFBox 3.x：
- `Loader.loadPDF(bytes)` 加载，`PDFTextStripper` 抽文本
- 默认支持 Unicode/中文，无需额外字体配置

**WordParser** — Apache POI 5.x：
- 先尝试 `.docx`（XWPFDocument），失败回退 `.doc`（HWPFDocument）
- 双格式覆盖，不需要调用方区分

**TxtParser** — 最简：
- `new String(bytes, UTF_8)` 直接读

**Spring 自动装配**：三个类都是 `@Component`，`DocumentServiceImpl` 用 `List<DocumentParser>` 注入，`parseFile()` 时根据 `FileType` 选对应的 Parser。

### 2.2 上传时同步解析

**涉及文件**: `DocumentServiceImpl.java`

**之前（异步方案，代码存在但未运行）**：
```
upload → MySQL(UPLOADED) → Redis LPUSH → Worker 出队 → 解析 → MySQL(PARSED)
```

**现在（同步方案，已运行）**：
```
upload → MySQL(UPLOADED) → parseFile() → MySQL(PARSED + content) → 返回 VO
```

核心改动在 `upload()` 方法尾部：

```java
// ④ 同步解析
try {
    String content = parseFile(entity);
    documentMapper.updateParseResult(fileId, "PARSED", content);
    log.info("文档解析成功: fileId={}, 长度={}字符", fileId, content.length());
} catch (Exception e) {
    String msg = e.getMessage() != null ? e.getMessage() : "解析异常";
    documentMapper.updateParseError(fileId, msg);
    log.warn("文档解析失败: fileId={}, 原因={}", fileId, msg);
}
```

兼容保留 `parse()` 方法，可以手动触发重新解析（也走同步不走队列）。

### 2.3 MySQL FULLTEXT 搜索

**涉及文件**: `DocumentMapper.java`、`DocumentServiceImpl.java`

两条搜索路径：

**① FULLTEXT 索引搜索（优先）**：
```sql
SELECT file_id, file_name, content,
       MATCH(content) AGAINST(#{keywords} IN NATURAL LANGUAGE MODE) AS relevance
FROM document
WHERE MATCH(content) AGAINST(#{keywords} IN NATURAL LANGUAGE MODE)
  AND status = 'PARSED'
ORDER BY relevance DESC
LIMIT #{maxResults}
```

MySQL 自带相关性打分，0~1 之间，按分降序。

**② LIKE 兜底（补充）**：
```sql
SELECT ... WHERE content LIKE CONCAT('%', #{keywords}, '%')
```

当 FULLTEXT 结果不足 `maxResults` 时，用 LIKE 补充，去重合并。

**片段截取**：搜到的结果从 `content` 中截取关键词前后各 60~140 字的上下文片段。（后改为 5000 字：对 5000 字以内的小文档全文返回，LLM 能看到完整条文，无需多次搜索补全上下文）

### 2.4 微信文件消息链路

**涉及文件**: `WechatServiceImpl.java`

**之前**：
```java
case 4 -> {
    // 文件消息预留
    log.info("[微信文件] 暂不处理: {}", fromUser);
}
```

**现在**：
```java
case 4 -> {
    if (item.getFile_item() != null) {
        handleFileMessage(fromUser, item);
    }
}

private void handleFileMessage(String fromUser, MessageItem item) {
    // ① 下载（SDK 自动解密）
    byte[] fileBytes = client.downloadFileFromMessageItem(item);
    
    // ② 获取/创建会话
    SessionEntity session = sessionService.getOrCreateActiveSession(fromUser);
    
    // ③ 上传并同步解析
    DocumentVO vo = documentService.upload(fromUser, session.getSessionId(), fileName, fileBytes);
    
    // ④ 走 AI 引擎回复用户（LLM 知道文件存在，自动选工具）
    callAiEngine(fromUser, "我上传了一个文件：「xxx」(fileId=f_xxx)，已解析完成", "FILE");
}
```

**关键设计**：文件消息不走 `client.sendText()` 直接回复，而是**走 AI 引擎**。LLM 收到"我上传了一个文件"后，知道有 `searchDocument` 和 `getDocumentSummary` 两个 @Tool 可用，用户再问"这里面写了什么"时自动调工具搜索。

### 2.5 会话模块实现

**涉及文件**: `SessionServiceImpl.java`、`SessionMapper.java`

`getOrCreateActiveSession()` 完整实现：

```java
public SessionEntity getOrCreateActiveSession(String userId) {
    // ① 查活跃会话（数据库比较 expire_at > NOW()）
    SessionEntity session = sessionMapper.findActiveByUserId(userId);
    
    if (session != null) {
        // ② 有活跃会话 → 续期 24 小时
        sessionMapper.refreshExpireTime(session.getSessionId(), LocalDateTime.now().plusHours(24));
        return session;
    }
    
    // ③ 没有 → 创建新会话（UUID，24h 过期）
    SessionEntity newSession = new SessionEntity();
    newSession.setSessionId(UUID.randomUUID().toString());
    newSession.setUserId(userId);
    newSession.setSource(SessionSource.WECHAT);
    newSession.setStatus(SessionStatus.ACTIVE);
    newSession.setExpireAt(LocalDateTime.now().plusHours(24));
    sessionMapper.insert(newSession);
    return newSession;
}
```

Mapper 也补全了 MyBatis 注解（之前是全空的接口定义）。

## 五、架构决策记录

### 5.1 同步解析 vs 异步队列

- **决策时间**: 2026-07-19 下午
- **背景**: 文档解析原设计走 Redis 异步队列（LPUSH → Worker 出队），但 `RedisTaskQueue`、`DocParseWorker`、`TaskService` 全是 TODO
- **决策**: 改为同步解析，upload 后当场调 Parser
- **依据**:
  - 第一期数据量小，50MB PDF 解析最多几秒，用户可接受
  - 去掉 Redis 依赖（本地开发环境可能没装 Redis）
  - 代码量少 3 倍，不需要维护 Worker 线程生命周期
  - 以后要异步再拆回去，接口签名不动

### 5.2 搜索方案

- **决策时间**: 2026-07-19 下午
- **背景**: 需要 AI 能搜索已解析文档内容
- **决策**: MySQL FULLTEXT 索引 + LIKE 兜底
- **依据**:
  - 零额外依赖（MySQL 自带）
  - 中文分词靠 MySQL 内置，一期够用
  - FULLTEXT 不够的用 LIKE 补，去重合并

### 5.3 SearchDocumentResult 放 common

- **决策时间**: 2026-07-19 下午
- **背景**: DocumentService 的 `search()` 返回 `SearchDocumentResult`，但 `SearchDocumentResult` 在 tool 模块，tool 又依赖 document → 循环依赖
- **决策**: 从 `wechat-ai-tool/model/dto/` 移到 `wechat-ai-common/model/dto/`
- **依据**: common 模块不依赖任何业务模块，所有模块都依赖 common，放这里谁都能用
