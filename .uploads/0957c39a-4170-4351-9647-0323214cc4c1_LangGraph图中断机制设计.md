## 1. 为什么需要图中断

### 1.1 当前问题

WRITE 类型工具（sendMessage、setRemind、sendEmail、generateDocument 等）有副作用，但当前架构中 LLM 调工具 = 直接执行：

```
用户："发邮件给 xxx@qq.com 说合同签了"
  → LLM 调用 sendEmail → 立即发出 → 回复"已发送"
  → ❌ 用户没有机会说"不"
```

### 1.2 图中断解决什么

- **系统级保障**：WRITE 工具执行前自动暂停，LLM 无法绕过
- **统一体验**：所有 WRITE 工具走同一套确认流程
- **零感知**：LLM 不需要知道 WRITE/READ 的区别，由注解 + 扫描自动识别
- **可扩展**：后续加新 WRITE 工具只需加一行 `@WriteTool` 注解

## 2. 现状 vs 目标

| 维度 | 当前（自然语言确认） | 目标（图中断） |
|------|:-------------------:|:--------------:|
| 保障方式 | Skill 规则约束 LLM 先问再调 | **系统级中断，LLM 无法绕过** |
| 可靠性 | 低（LLM 可能跳过） | 高 |
| 用户体验 | 依赖 LLM 生成问句，不一致 | **统一确认格式** |
| 实现复杂度 | 零代码 | ~200 行代码 |
| LLM 感知 | 需要提示词告诉 LLM 先问 | **完全无感知，直接调工具即可** |
| 新增 WRITE 工具 | 需同步改提示词 + Skill | **加一行 `@WriteTool` 注解** |

## 3. LangGraph4j 中断 API 分析

基于 langgraph4j-core **1.8.18** 版本（通过反编译 `.jar` 验证）。

### 3.1 核心类

| 类 | 作用 |
|----|------|
| `CompileConfig` | 编译配置，设 `interruptBefore` / `interruptAfter` 中断点 |
| `CompileConfig.Builder.interruptBefore("node_name")` | 指定在某个节点执行**前**中断 |
| `CompiledGraph` | 编译后的可执行图，缓存而非每次都 `compile()` |
| `MemorySaver` | 内存级 checkpoint 保存器，中断时自动保存 state |
| `BaseCheckpointSaver` | Checkpoint 保存器接口（MemorySaver 实现，可替换为 MySQL） |
| `RunnableConfig` | 运行配置，含 `threadId` / `checkPointId` |
| `StateSnapshot` | 通过 `CompiledGraph.getState(config)` 获取中断时的状态快照 |
| `Checkpoint` | 检查点，含 `getState()` 返回中断时的完整 `Map` |

### 3.2 中断配置 API

```java
// 编译时设中断
MemorySaver saver = new MemorySaver();
CompileConfig config = CompileConfig.builder()
    .interruptBefore("tool_execute")     // ← 执行 tool_execute 前中断
    .checkpointSaver(saver)
    .build();
CompiledGraph<ChatGraphState> compiled = graph.compile(config);

// 第一次执行
RunnableConfig runConfig = RunnableConfig.builder()
    .threadId("unique_id")               // ← 标识这个执行线程
    .build();
compiled.invoke(initData, runConfig);

// 恢复执行（第二次）
compiled.invoke(null, runConfig);        // null → 从上次中断点继续
```

### 3.3 Checkpoint 生命周期

```
第一次 invoke (initData, config)
  → 执行节点，直到 interruptBefore 点
  → MemorySaver 保存 state（keyed by threadId）
  → 图暂停，invoke() 返回当前 state

第二次 invoke (null, config)  ← resume
  → MemorySaver 读到对应 threadId 的 checkpoint
  → 从暂停处继续执行
  → 完成后 checkpoint 保留（可再次查询）
```

## 4. 整体架构设计

### 4.1 关键设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 如何标记 WRITE 工具 | `@WriteTool` 注解 + 扫描时自动填充 `ToolCategory` | 组员加新工具只需加注解，零额外成本 |
| 图中断检测方式 | 按 `finishReason=TOOL` + 有 pending tools | 排除 MemorySaver 的残留旧检查点数据 |
| threadId 策略 | 每次新消息用唯一 threadId（`userId_自增序号`） | 彻底避免旧检查点字段污染新请求 |
| 取消方式 | `updateState()` 注入假 tool result + 恢复图执行 | 让 LLM 自然结束，不产生孤立 tool_call |
| LLM 提示词 | 完全不提 WRITE/系统确认 | 中断是系统级能力，LLM 不需要知道 |

## 5. 实现方案详解

### 5.1 `@WriteTool` 注解

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
public @interface WriteTool {
    String value() default "";
}
```

组员新增 WRITE 工具时在类上加上：
```java
@Component
@WriteTool("发送电子邮件")
public class SendEmailTool { ... }
```

### 5.2 `ToolRegistryImpl` — 自动识别分类

在 `scanToolBeans()` 中，扫描到 `@Tool` 方法时：

```java
if (beanClass.isAnnotationPresent(WriteTool.class)) {
    def.setCategory(ToolCategory.WRITE);
} else {
    def.setCategory(ToolCategory.READ);
}
```

### 5.3 `ChatGraphConfig` — 编译图注入

定义两个 Bean：
- `simpleChatGraph` — 图结构定义（节点 + 边），和原来一样
- `compiledChatGraph` — 编译后单例，注入 `MemorySaver` + `interruptBefore`

```java
@Bean
public CompiledGraph<ChatGraphState> compiledChatGraph(
        StateGraph<ChatGraphState> simpleChatGraph) throws GraphStateException {
    MemorySaver saver = new MemorySaver();
    CompileConfig config = CompileConfig.builder()
            .interruptBefore("tool_execute")
            .checkpointSaver(saver)
            .build();
    return simpleChatGraph.compile(config);
}
```

### 5.4 `GraphInterruptHandler` — WRITE 检测 + 确认消息

```java
@Component
public class GraphInterruptHandler {

    private final ToolRegistry toolRegistry;

    /** 从 toolCalls 中找到第一个 WRITE 工具名 */
    public String findWriteToolName(List<Map<String, Object>> toolCalls) {
        List<ToolDefinitionVO> tools = toolRegistry.listTools(null, null);
        for (Map<String, Object> tc : toolCalls) {
            String name = (String) ((Map)tc.get("function")).get("name");
            for (ToolDefinitionVO def : tools) {
                if (name.equals(def.getName()) && def.getCategory() == ToolCategory.WRITE) {
                    return name;
                }
            }
        }
        return null;
    }

    /** 组装确认消息 */
    public String buildConfirmMessage(String toolName, String argsJson) {
        return "⚠️ 需要你确认以下操作：\n\n"
             + "操作：" + toolName + "\n"
             + "详情：\n" + formatArgs(toolName, argsJson) + "\n\n"
             + "回复「确认」或「是」执行，回复「取消」或「否」取消";
    }

    /** 关键词匹配 */
    public boolean isConfirm(String msg) { /* "确认"/"是"/"确定"等 */ }
    public boolean isCancel(String msg)  { /* "取消"/"否"/"不"等 */ }
}
```

### 5.5 `GraphStateStore` — 挂起状态存储

```java
@Component
public class GraphStateStore {

    private final Map<String, SuspendedContext> store = new ConcurrentHashMap<>();

    public void suspend(String userId, SuspendedContext ctx) { store.put(userId, ctx); }
    public SuspendedContext getSuspended(String userId) { return store.get(userId); }
    public void remove(String userId) { store.remove(userId); }

    @Scheduled(fixedRate = 60_000)
    public void cleanupExpired() {
        long deadline = System.currentTimeMillis() - 10 * 60 * 1000L;
        store.entrySet().removeIf(e -> e.getValue().getSuspendedAt() < deadline);
    }

    @Data
    @AllArgsConstructor
    public static class SuspendedContext {
        private String userId;
        private String sessionId;
        private String threadId;       // 用于恢复执行
        private String toolName;
        private String toolArgs;       // 用于展示
        private long suspendedAt;
    }
}
```

### 5.6 `WechatChatBridge.doThink()` — 核心流程

```java
private void doThink(String fromUser, String content, String messageType) {

    // A. 检查是否有挂起的确认
    SuspendedContext ctx = graphStateStore.getSuspended(fromUser);
    if (ctx != null) {
        handleSuspendedResponse(fromUser, content, ctx);
        return;
    }

    // B. 正常调用：每次使用唯一 threadId（避免 MemorySaver 旧数据污染）
    String threadId = fromUser + "_" + msgCounter.incrementAndGet();
    RunnableConfig config = RunnableConfig.builder().threadId(threadId).build();

    var result = compiledGraph.invoke(initData, config);

    if (result.isPresent()) {
        String finishReason = (String) rawData.get("finishReason");
        boolean hasPendingTools = /* rawData 中有 toolExecutionRequests 且非空 */;

        if (hasPendingTools && "TOOL".equals(finishReason)) {
            // C. 图中断！→ 检查 WRITE → 挂起或自动恢复
            handleInterrupt(fromUser, threadId);
        } else {
            // D. 正常完成 → 发回复
            syncUserContexts(fromUser, state);
            sender.sendReply(fromUser, reply);
        }
    }
}
```

### 5.7 完整交互流程

```
用户："发邮件给 xxx@qq.com，内容为测试"
  │
  ▼
WechatInboundHandler.handleText()
  → chatBridge.think(fromUser, "发邮件给...")
  → doThink()
  │
  ├─ A. 检查 GraphStateStore → 无挂起
  │
  ├─ B. 生成唯一 threadId = "fromUser_1"
  │   invoke(initData, config)
  │
  ├─ C. 图执行：prepare_input → session_prepare → llm_think
  │   → LLM 返回 text + tool_calls(sendEmail)
  │   → finishReason=TOOL, hasPendingTools=true
  │   → 进入 handleInterrupt()
  │
  ├─ D. handleInterrupt():
  │   → compiledGraph.getState(config) 取快照
  │   → 从 state 提取 toolExecutionRequests
  │   → interruptHandler.findWriteToolName() → "sendEmail"
  │   → graphStateStore.suspend(userId, ctx)
  │   → 发⚠️确认消息给用户
  │
  ▼
用户回复："确定"
  │
  ▼
WechatInboundHandler.handleText()
  → chatBridge.think(fromUser, "确定")
  → doThink()
  │
  ├─ A. 检查 GraphStateStore → 有挂起！
  │   → handleSuspendedResponse()
  │   → isConfirm("确定") = true
  │   → resumeGraph(savedThreadId, fromUser)
  │
  ├─ B. resumeGraph():
  │   → invoke(null, config)  ← 用挂起时保存的 threadId
  │   → MemorySaver 找到 checkpoint
  │   → 从 tool_execute 继续执行
  │   → sendEmail() → 发出邮件
  │   → llm_think → LLM 回复"已发送"
  │   → END
  │   → sender.sendReply(fromUser, "邮件已成功发送到...")
```

## 6. 恢复流程详解

### 6.1 恢复原理

```java
private void resumeGraph(String threadId, String fromUser) {
    RunnableConfig config = RunnableConfig.builder()
            .threadId(threadId)     // ← 用挂起时保存的原 threadId
            .build();

    var result = compiledGraph.invoke(null, config);
    // null → MemorySaver 查找 threadId 对应的 checkpoint
    // → 从 tool_execute 继续执行

    if (result.isPresent()) {
        syncUserContexts(fromUser, state);
        sender.sendReply(fromUser, reply);
        graphStateStore.remove(fromUser);
    } else {
        // 恢复后再次中断 → 递归处理
        handleInterrupt(fromUser, threadId);
    }
}
```

### 6.2 threadId 策略

```
正常新消息：threadId = "fromUser_1", "fromUser_2", "fromUser_3"...
  每次唯一，MemorySaver 按 threadId 隔离，旧数据不会污染新请求

挂起后恢复：threadId = 挂起时保存的 threadId
  MemorySaver 中该 threadId 还有 checkpoint → 精确恢复中断点

图正常完成后：不对该 threadId 做任何操作
  唯一 threadId 已用完即弃，MemorySaver 自动 GC
```

## 7. 取消流程详解

### 7.1 取消处理

```java
private void cancelGraph(String fromUser, SuspendedContext ctx) {
    RunnableConfig config = RunnableConfig.builder()
            .threadId(ctx.getThreadId())
            .build();

    // 1. 获取当前 checkpoint
    var snapshot = compiledGraph.getState(config);
    if (snapshot != null) {
        ChatGraphState state = snapshot.state();
        List<Map<String, Object>> messages = /* 从 state 取 messageHistory */;

        // 2. 注入假 tool result → 告诉 LLM 用户取消了
        Map<String, Object> cancelResult = new LinkedHashMap<>();
        cancelResult.put("role", "tool");
        cancelResult.put("tool_call_id", "user_cancelled");
        cancelResult.put("content", "用户已取消此操作，请回复已知晓");
        messages.add(cancelResult);

        // 3. updateState：清空待执行工具 + 注入取消消息
        Map<String, Object> updates = new HashMap<>();
        updates.put("messageHistory", messages);
        updates.put("toolExecutionRequests", new ArrayList<>());
        updates.put("needTool", false);
        compiledGraph.updateState(config, updates);
    }

    // 4. 恢复图 → tool_execute 无事可做 → llm_think 生成回复
    compiledGraph.invoke(null, config);

    // 5. 通知用户
    graphStateStore.remove(fromUser);
    sender.sendReply(fromUser, "已取消" + ctx.getToolName() + "操作");
}
```

### 7.2 超时清理

```java
/** 10 分钟自动清理过期挂起 */
@Scheduled(fixedRate = 60_000)
public void cleanupExpired() {
    long deadline = System.currentTimeMillis() - 10 * 60 * 1000L;
    store.entrySet().removeIf(e -> {
        boolean expired = e.getValue().getSuspendedAt() < deadline;
        if (expired) log.warn("【挂起超时】已自动清理 userId={}", e.getKey());
        return expired;
    });
}
```

### 7.3 取消/超时后的状态

- `GraphStateStore`：删除了 userId 的记录
- `MemorySaver`：checkpoint 仍然存在（无 remove API），但 threadId 唯一且不会复用，不影响后续

## 9. 关键 API 说明

### 9.1 interruptBefore vs interruptAfter

| 配置 | 含义 | 适用场景 |
|------|------|---------|
| `interruptBefore("tool_execute")` | 执行 tool_execute **前**中断 | 工具执行前让用户确认 |
| `interruptAfter("llm_think")` | 执行 llm_think **后**中断 | LLM 返回结果后人工审核 |

### 9.2 CompileConfig 完整配置项

```java
CompileConfig config = CompileConfig.builder()
    .interruptBefore("tool_execute")      // 中断点（节点名前）
    .interruptAfter("llm_think")          // 可同时设多个
    .checkpointSaver(memorySaver)         // 检查点保存器
    .recursionLimit(25)                   // 最大循环次数
    .graphId("wechat-graph")              // 图标识
    .build();
```

### 9.3 CompiledGraph 关键方法

| 方法 | 说明 |
|------|------|
| `invoke(Map, RunnableConfig)` | 正常执行图，传入初始状态 |
| `invoke(null, RunnableConfig)` | 恢复执行，从中断点继续 |
| `getState(RunnableConfig)` | 获取指定 threadId 的状态快照（含中断时的 state） |
| `updateState(RunnableConfig, Map)` | 更新指定 threadId 的 checkpoint 状态 |

### 9.4 MemorySaver vs 自定义 Saver

| Saver | 生命周期 | 适用阶段 | 说明 |
|-------|---------|:--------:|------|
| `MemorySaver` | JVM 内存 | 当前实现 | 简单可靠，重启丢失 |

### 9.5 用户确认/取消关键词

```java
确认：确认、是、确定、嗯、好、发、以"确认"开头、以"是 "开头
取消：取消、否、不、算了、别、以"取消"开头、以"否 "开头
```

## 10. 技术风险与应对

| # | 风险 | 影响 | 应对方案 |
|---|------|------|---------|
| 1 | 重启后 MemorySaver 丢失 | 重启后挂起的确认全部丢失 | 第一阶段接受（内存方案），后续升级持久化 |
| 2 | MemorySaver 无 remove API | 取消后 checkpoint 残留 | 用唯一 threadId，旧 checkpoint 自动 GC |
| 3 | 恢复后 LLM 生成孤立 tool_call | 后续消息报 400 错误 | `cleanupOrphanedToolCalls()` 自动清理 |
| 4 | 旧 checkpiont 字段污染新请求 | 上个 thread 的 reply/toolExecutionRequests 残留在下个请求 | 每次新消息用唯一 threadId |
| 5 | 中断和正常消息并发 | 消息顺序错乱 | 同一用户走单线程池，天然串行 |
| 6 | `CompiledGraph` 单例线程安全 | 多用户并行调用问题 | MemorySaver 内部用 `ConcurrentHashMap`，threadId 隔离 |

## 11. FAQ

### 为什么不用"在图上插入一个确认节点"的方案？

插入确认节点需要手动做三件事，图中断机制自动做了：
1. 手动存 tool_call 信息到 DB/内存 → `MemorySaver` 自动 checkpoint
2. 手动写 confirm 节点读取挂起工具参数 → `interruptBefore` + `getState()` 拿到快照
3. 用户确认后跳过执行 → `invoke(null, config)` 自动从断点继续

图中断是 LangGraph4j 原生支持的拦截机制，更贴合框架设计。

### LLM 提示词中为什么不提 WRITE/系统确认？

图中断不依赖 LLM 理解——它扫描的是 `@WriteTool` 注解。提示词里提 WRITE 反而会让 LLM 以为自己需要做确认，导致画蛇添足（LLM 先问一遍，系统再拦一遍）。

### 组员加新工具需要做什么？

```java
// WRITE 工具加一行注解
@Component
@WriteTool("操作说明")
public class XxxTool { ... }

// READ 工具什么都不加（默认 READ）
@Component
public class YyyTool { ... }
```
