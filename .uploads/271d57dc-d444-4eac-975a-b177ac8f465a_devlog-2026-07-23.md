## 概述

上午：实现了 LangGraph 图中断/恢复机制。WRITE 类型工具（发邮件、生成文档、设置提醒等）在执行前自动暂停，等待用户确认后放行。基于 langgraph4j-core 1.8.18 的 `interruptBefore` + `MemorySaver` API，LLM 完全无感知，由 `@WriteTool` 注解 + 系统级扫描自动识别。

下午-晚：多 Agent 协作实验 Phase 1 骨架搭建。纯指挥官模式（Orchestrator 不暴露原子工具，只暴露 Worker），新建 `wechat-ai-agent` 模块（ai/tool 不动），10 个新文件 + 3 处修改。编译通过，运行时存在 ToolRegistryImpl 循环依赖问题未解决。

最终效果：用户说"发邮件给xxx" → LLM 直接调 sendEmail（不需要知道中断存在）→ 图中断拦截发 ⚠️ 确认 → 用户回复"确定" → 工具执行成功。

## 三、技术方案详解

### 3.1 整体架构

```
┌─────────────────────────────────────────────────────┐
│  @WriteTool 注解 + ToolRegistryImpl 自动扫描          │
│  → ToolDefinitionVO.category = WRITE 或 READ         │
└─────────────────────┬───────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────┐
│  CompiledGraph (MemorySaver + interruptBefore)       │
│  → tool_execute 前自动暂停 → MemorySaver 存 checkpoint │
└─────────────────────┬───────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────┐
│  WechatChatBridge.doThink()                          │
│  ├─ ① check GraphStateStore → 有挂起? → 确认/取消    │
│  ├─ ② 唯一 threadId invoke → 正常完成? → 发回复      │
│  └─ ③ 图中断! → GraphInterruptHandler 检查 WRITE     │
│        ├─ 有 WRITE → GraphStateStore.suspend() + ⚠️  │
│        └─ 纯 READ  → 自动 resume                     │
└─────────────────────────────────────────────────────┘
```

### 3.2 WRITE 工具识别机制

**不依赖 LLM**，完全靠代码级注解：

```java
// 组员加新 WRITE 工具只需一行注解
@Component
@WriteTool("发送电子邮件")
public class SendEmailTool { ... }

// 不加 @WriteTool 的默认 READ
@Component
public class QueryWeatherTool { ... }
```

`ToolRegistryImpl` 在 `scanToolBeans()` 中自动识别并填充 `ToolCategory`。

### 3.3 图中断检测逻辑

```
invoke() 返回后检查 state：
  ├─ hasPendingTools == false → 正常完成，发回复
  ├─ hasPendingTools == true && finishReason == TOOL → 图中断！
  │     → getState() 取快照 → findWriteToolName()
  │     ├─ 找到 WRITE → GraphStateStore.suspend() + 发确认消息
  │     └─ 全 READ   → autoResume()
  └─ hasPendingTools == true && finishReason == STOP → MemorySaver 残留旧数据
        → 正常完成，忽略（唯一 threadId 方案已解决此问题）
```

### 3.4 threadId 策略（关键设计）

| 方案 | 问题 | 最终 |
|------|------|------|
| `threadId = userId`（固定） | MemorySaver 旧 checkpoint 的 reply/toolExecutionRequests 随相同 threadId 继承到新请求 | ❌ |
| 每次新消息用唯一 `userId_自增序号` | 彻底隔离检查点，旧数据不污染新请求，中断时保存的 threadId 精确指向中断点 | ✅ |

### 3.5 取消实现

用户取消时，不是直接丢弃 checkpoint 完事——那样会在 messageHistory 中留下孤立的 assistant.tool_calls，后续调用报 400 错误。

```java
// 取消流程
cancelGraph():
  → 1. getState() 取 checkpoint
  → 2. updateState() 注入假 tool result → "用户已取消此操作"
  → 3. invoke(null) 恢复图 → tool_execute 无事可做 → llm_think
  → 4. LLM 生成"已取消"回复 → 图正常结束
```

### 3.6 清理孤立 tool_call

```java
cleanupOrphanedToolCalls():
  → 扫描 messageHistory
  → 找到 assistant 消息中未被 tool 消息跟上的 tool_calls
  → 移除 tool_calls 字段，保留 content
```

## 四、调试记录

### 4.1 启动失败：循环依赖

```
错误: The dependencies of some beans form a cycle:
  graphInterruptHandler → toolRegistryImpl
  toolRegistryImpl → graphInterruptHandler
```

- **原因**: `GraphInterruptHandler` 注入 `ToolRegistry`，`ToolRegistryImpl` 扫描 Bean 时触发 `GraphInterruptHandler` 创建
- **解决**: `GraphInterruptHandler` 构造器参数加 `@Lazy`

### 4.2 中断检测不触发

```
invoke() 返回 reply='null', hasPendingTools=true, finishReason=TOOL
但走了"正常完成"分支，没发任何消息
```

- **原因**: 代码判断 `if (result.isPresent())` 就走正常完成，但图中断时 invoke 返回的是当前 state（非空）而不是 `Optional.empty()`
- **解决**: 改为判断 `hasPendingTools && finishReason==TOOL` 才走中断

### 4.3 MemorySaver 字段污染

```
第1轮：用户说"发邮件" → invoke → 中断 → 发确认消息
第2轮：用户说"确定" → invoke → 读到了第1轮的旧 reply → 误判
```

- **原因**: 固定 threadId 导致 MemorySaver 旧检查点字段继承到新请求
- **解决**: 每次新消息用唯一 threadId（`userId_自增序号`）

### 4.4 双轮确认问题

```
用户说"发邮件"
第1轮：LLM 回复"您确认吗？"（没有调工具）
第2轮：用户回复"确定" → LLM 调 sendEmail → 系统拦截再次确认
```

- **原因**: LLM 提示词和 `@Tool` 描述中写了"必须先问用户确认"，系统层和 LLM 层各问一遍
- **解决**: 从 `@Tool` 描述 / `EmailSkill` / `SystemPrompt` 中完全清除"先问用户"表述。中断是系统层能力，LLM 不需要知道。

### 4.5 400 错误：孤立 tool_call

```
"An assistant message with 'tool_calls' must be followed by tool messages"
```

- **原因**: 中间某个异常或中断导致 history 中出现 `assistant.tool_calls` 但没有对应的 `tool` 消息
- **解决**: 每次新消息前调用 `cleanupOrphanedToolCalls()` 修复

### 4.6 READ 工具链式调用死循环

```
resumeGraph() 恢复后 LLM 又调 searchInternet → 再中断 → 再恢复 → 调 readUrl → ...
无限循环（最多 10 次后报错终止）
```

- **原因**: `resumeGraph()` 恢复后只执行一次 `invoke(null)`，如果 LLM 链式调用第二个工具（searchInternet → readUrl），再次中断时直接走"正常完成"分支，第二个工具没执行，LLM 又重试，陷入死循环
- **解决**: `resumeGraph()` 改为循环，恢复后再中断时检查是 READ 还是 WRITE，READ 自动继续恢复，WRITE 才挂起等用户确认

### 4.7 SearXNG 搜索升级尝试（放弃）

- **尝试**: 自建 SearXNG 搜索引擎替代 Bing 爬取，Docker 部署在阿里云服务器
- **结果**: SearXNG 默认 403 限制无法关闭，改配置后仍返回 403，API JSON 格式和网页爬取均被拦截
- **结论**: 回滚到 Jsoup 爬 Bing 方案，稳定第一
- **备注**: SearXNG 容器已删除

## 六、设计决策记录

### 6.1 @WriteTool 注解标记

- **决策时间**: 2026-07-23 上午
- **方案对比**:

| 方案 | 工作量 | 组员感知 | 容错 |
|------|--------|---------|------|
| `@WriteTool` 注解 | 3 分钟（新建 + 扫描 + 演示） | 加新 WRITE 工具时加一行 | 低——不加就默认 READ |
| 工具名称硬编码 | 0（硬编码"sendEmail"等） | 零感知 | 高——漏加新工具不会误放行 |
| 按工具分类枚举 | 0（已有 ToolCategory 枚举但没填充） | 只加注解不分类别 | 中 |

- **最终选择**: `@WriteTool` 注解 + `ToolRegistryImpl` 自动分类
- **原因**: 和 `@Tool` 注解的用法一致，组员学习成本最低；后续配合 IDE 插件还能自动提示

### 6.2 图结构不动

- **决策时间**: 2026-07-23 上午
- **方案对比**:

| 方案 | 工作方式 | 复杂度 |
|------|---------|--------|
| 图上加确认节点 | 插入一个"confirm"节点，检查 Confirmed flag | 中——需改图结构 + 写节点 |
| **interruptBefore 编译配置** | 声明式的拦截，图结构不变 | **低——框架原生支持** |

- **最终选择**: `interruptBefore("tool_execute")` + `CompiledGraph` 单例
- **原因**: LangGraph4j 的 `interruptBefore` 本质就是"在门口停一下"，不需要在图上开一个确认节点。框架自动 checkpoint、自动恢复。

### 6.3 唯一 threadId 方案

- **决策时间**: 2026-07-23 上午-下午（调试中发现）
- **过程**: 最初用固定 userId 作为 threadId → MemorySaver 旧数据污染 → 改为唯一 threadId
- **影响**: 恢复时必须用挂起时保存的原 threadId，`SuspendedContext` 中保存 `threadId` 字段

### 6.4 LLM 提示词零感知

- **决策时间**: 2026-07-23 下午
- **原因**: 图中断完全不依赖 LLM 理解，提示词中写 WRITE/系统确认反而误导 LLM 自己先问一遍
- **方案**: 所有 WRITE 相关提示词全部删除，LLM 只管调工具

#### 运行时错误（未解决）

启动成功，发送消息后触发循环依赖报错：

```
链路：
  ToolRegistryImpl.@PostConstruct
    → getBean("orchestratorTools")
      → 即使 @Lazy + ObjectProvider<AgentInvoker>，AgentInvoker 本身仍需初始化
        → AgentInvoker 注入 ObjectProvider<AgentToolRegistry>
          → AgentToolRegistry 构造函数需要 ToolRegistry
            → toolRegistryImpl 正在跑 @PostConstruct → BeanCurrentlyInCreationException
```

**已加的规避措施**：
- `OrchestratorTools` → `@Lazy` + `ObjectProvider<AgentInvoker>`
- `AgentInvoker` → `@Lazy` + `ObjectProvider<AgentToolRegistry>`
- `AgentToolRegistry` → `@Lazy`

**剩余问题**：`ToolRegistryImpl.scanToolBeans()` 中对 `applicationContext.getBean(beanName)` 的调用是强制初始化的——即使 bean 标记了 `@Lazy`，`getBean()` 也会触发完整的依赖解析链。这导致最终运行时仍炸。

**待修复方向**：
- 让 `ToolRegistryImpl.scanToolBeans()` 跳过 agent 模块的 bean（黑名单/白名单）
- 或者把 `OrchestratorTools` 移出 tool 扫描范围（不在类上加 `@Component`，改为手动注册）
- 或者不依赖 `ToolRegistryImpl` 自动扫描，用独立注册方式注册 Orchestrator 的工具
