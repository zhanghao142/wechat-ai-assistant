## 二、今日开发内容

### Bug 1：assistant 回复未存入 messageHistory

**涉及文件**: `LlmService.java`（普通回复分支）

**发现问题**：验证多轮对话时发现，第 1 轮正常回复后，第 2 轮 LLM 不记得自己说过什么。

**根因**：

```java
// 有 tool_calls 时：
messages.add(assistantMsg);       // ✅ 有加
result.put("messageHistory", messages);

// 普通回复时：
result.put("messageHistory", messages);  // ❌ 没加 assistantMsg！
```

`hasToolCalls` 分支有 `messages.add(assistantMsg)`，普通回复分支漏了这行。

**修复**：

```java
} else {
    log.info("【LLM】回复 ({}ms): {}", elapsed, content);
    messages.add(assistantMsg);                  // ✅ 补上
    result.put("messageHistory", messages);
}
```

**修复效果**：第 2 轮"杭州天气咋样"拿到的 history 中包含第 1 轮的 assistant 回复，LLM 知道上下文完整。

### Bug 2：ReAct 循环中 user 消息重复追加

**涉及文件**: `LlmService.java`（有历史时的消息追加逻辑）

**发现问题**：观察日志发现调了工具的这轮里，`messageHistory` 出现多条重复的 `user(杭州天气咋样)`。

**根因**：

```
llm_think (第1次进入)
  → messages 不为 null → else 分支 → 追加 user(天气)     ✅ 正确
  → 返回 tool_calls

tool_execute
  → 追加 tool(结果)

llm_think (第2次进入 — ReAct 循环回来的)
  → messages 仍然不为 null → else 分支 → 又追加 user(天气)  ❌ 重复！
```

`state.getUserMessage()` 在整个图生命周期内固定为"杭州天气咋样"，ReAct 循环二次进入时无条件追加，导致重复。

**修复**：

```java
} else {
    // 最后一条是 tool 说明在 ReAct 循环中，跳过追加
    if (messages.isEmpty() || !"tool".equals(messages.get(messages.size() - 1).get("role"))) {
        messages.add(Map.of("role", "user", "content", state.getUserMessage()));
    }
}
```

**判断逻辑**：

| 场景 | 最后一条 role | 是否追加 | 说明 |
|------|--------------|---------|------|
| 首轮正常对话 | `assistant` | ✅ | 新的一轮，加用户消息 |
| ReAct 循环回来 | `tool` | ⛔ | 用户消息已加过 |
| 连续多次调工具 | `tool` | ⛔ 每次 | 都在循环中，都跳过 |
| 新 invoke | `assistant` | ✅ | 上轮结束一定以 assistant 结尾 |

### 识图提示词优化（QwenVLService）

**涉及文件**: `QwenVLService.java`

**旧提示词**：
```
请用简洁的语言描述这张图片中的内容，包括物体、场景、人物、动作等。控制在50字以内。
```

**新提示词**（结构化三块输出）：
```
【文字】如果图片中有文字，完整提取出来（最优先）。没有则写"无"。
【描述】用一句话概括图片内容
【类型】照片/截图/表情包/二维码/文档/其他
```

**输出示例**（照片场景）：
```
1. 【文字】冰红茶 丝柔 亲肤 4层
2. 【描述】一张桌子上放着一瓶冰红茶、一包纸巾和一个无线耳机盒
3. 【类型】照片
```

**优化要点**：
- 文字提取优先级最高 → 截图/文档场景 LLM 直接看到文字内容
- 类型判断 → 表情包识别后 LLM 自然回应，二维码不会尝试解码
- 不再限制 50 字 → 调整为 100 字

### SYSTEM_PROMPT 图片处理规则补充

**涉及文件**: `LlmService.java`（`SYSTEM_PROMPT` 常量）

**问题**：用户只发图不提问时，LLM 掉入了"未找到信息"的回复格式。

**改动**：

| 项 | 旧 | 新 |
|----|----|----|
| 红线 | ❌ 不要主动复述或描述图片内容 | ❌ 不要啰嗦描述，一句话带过即可 |
| 图片规则 | 无 | 用户发图+提问 → 正常回答，图片当背景 |
| 图片规则 | 无 | 用户只发图不提问 → 一句话说说图片里是什么，然后问需要什么 |
| 禁止项 | 无 | ❌ 禁止用"未找到内容"回应图片消息 |

### AI 引擎调用异步化

**问题**：poll 线程同步跑 `callAiEngine`（耗时 3-5 秒），期间 SDK 内部消息标记为已消费，导致后续消息丢失。

**解决**：每个用户独立单线程池，`callAiEngine` 投递到后台执行：

```java
private final Map<String, ExecutorService> userExecutors = new ConcurrentHashMap<>();

private void callAiEngine(String fromUser, ...) {
    getExecutor(fromUser).submit(() -> {
        // 原来的 AI 调用逻辑
    });
}
```

**当前风险**：图片消息的下载和 Qwen-VL 识别仍在 poll 线程同步执行，小概率仍有消息丢失。待后续修复。

## 五、架构决策记录

### 5.1 消息历史追加判断规则

- **决策时间**: 2026-07-18 下午
- **背景**: ReAct 循环中 llm_think 会多次进入，`userMessage` 固定不变，无条件追加导致重复
- **决策**: 当消息列表最后一条 role 为 `tool` 时跳过追加
- **依据**: `tool` 只出现在 ReAct 循环中（tool_execute 写入的），新 invoke 最后一条一定是 `assistant`，不会误拦

### 5.2 识图提示词结构化

- **决策时间**: 2026-07-18 上午
- **背景**: 旧提示词只做场景描述，截图/文档场景下重要文字信息丢失
- **决策**: 改为三块结构化输出，文字提取优先级最高
- **依据**: LLM 按需取用，比纯描述更灵活，兼容多种图片类型
