## 三、WRITE 工具分类精简

### 问题

`navigate` / `click` / `fill` / `goBack` / `goForward` 被列为 WRITE，每次操作都要用户确认。但这些只是浏览器操作，不产生持久化数据，导致用户体验极差（打开百度都要确认）。

### 修复

`ToolRegistryImpl.WRITE_TOOLS` 从 8 个精简为 2 个：

| 改前（WRITE） | 改后（WRITE） |
|--------------|--------------|
| `setRemind`, `sendEmail`, `generateDocument` | `setRemind`, `sendEmail`, `generateDocument` |
| `transformContent`, `navigate`, `click`, `fill`, `screenshot`, `goBack`, `goForward` | → `transformContent`, `screenshot` 保留 WRITE |
| | → `navigate`, `click`, `fill`, `goBack`, `goForward` **改为 READ** |

### 效果

浏览器导航、点击等操作不再需要用户确认，直接执行。只有截图（生成文件）和内容转换（修改内容）才需要确认。

## 四、Playwright 超时优化

### 问题

百度等广告多的页面加载慢，`waitForLoadState(NETWORKIDLE)` 因广告脚本持续请求而超时。

### 修复

| 文件 | 改前 | 改后 |
|------|------|------|
| `BrowserProperties.java` | `pageLoadTimeout = 15000` | **30000**（30s） |
| `BrowserTool.java`（6 处） | `LoadState.NETWORKIDLE` | **`LoadState.LOAD`** |

`LOAD` 只等页面框架加载完，不等广告/统计脚本，大幅减少超时概率。

## 七、滴滴出行 MCP 接入（v2.17）

### 背景

LangChain4j 升级到 1.7.1 后，`langchain4j-mcp` 模块最高版本为 `1.0.0-beta5`，但该版本只支持旧版 SSE 传输层，滴滴 MCP Server 使用的是新版 Streamable HTTP 协议，握手失败（`Invalid content-type: text/plain`）。

**决策**：不使用 `langchain4j-mcp` 库，改用 `RestClient` 直调 JSON-RPC 2.0。

### 架构

```

wechat-ai-tool/mcp/
├── McpConfigProperties.java    # @ConfigurationProperties mcp.didi.*
├── McpClientManager.java       # 连接管理 + tools/list + tools/call
└── McpToolBridge.java           # ApplicationReadyEvent → 注册到 ToolRegistry

```

### 调用流程

```

用户发"帮我叫车从A到B"
  → LlmService.think() 发 40 个工具给 DeepSeek
  → DeepSeek 选 maps_textsearch + taxi_estimate + taxi_create_order
  → ToolExecuteNode:
      ① maps_textsearch → isExternalTool → McpClientManager → 滴滴 API
      ② taxi_estimate → isExternalTool → McpClientManager → 滴滴 API
      ③ taxi_create_order → isExternalTool → McpClientManager → 滴滴 API
         → 途中被图中断拦截（WRITE），等用户确认

```

### 设计要点

| 要点 | 说明 |
|------|------|
| **零依赖** | 只用 Spring `RestClient` + Jackson，不引入 MCP SDK |
| **统一注册** | MCP 工具通过 `registerExternalTool()` 进入 ToolRegistry，对 LLM 透明 |
| **执行路由** | `ToolExecuteNode` 先判断 `isExternalTool()`，再走本地反射 |
| **图中断** | `McpToolBridge.WRITE_MCP_TOOLS` 标记下单/取消为 WRITE，走确认流程 |
| **DB 链完整性** | 所有路径（成功/失败/取消）都写 TOOL_RESULT 到 message 表 |
| **取消后清理** | 取消后 LLM 若生成新 tool_call，自动清理防止 400 |

### 确认消息优化

`buildTaxiConfirmMessage()` 从 messageHistory 中提取：
- 起终点名 ← `taxi_estimate` 的参数（`from_name`/`to_name`）
- 车型中文名 ← `product_category` 映射（191→惊喜特价）
- 预估价格 ← 只显示所选车型的那一行价格

### 对比 langchain4j-mcp 方案

| 维度 | langchain4j-mcp 库 | RestClient 直调 |
|:----|:------------------|:----------------|
| 原理 | 库封装 MCP 协议握手+SSE+JSON-RPC | 手动构造 JSON-RPC 2.0 POST |
| 版本 | 最高 1.0.0-beta5（仅 SSE） | 无版本问题 |
| 依赖 | +langchain4j-mcp +okhttp-sse | 零额外依赖 |
| 可扩展性 | 受限于库的 API（`HttpMcpTransport`、`DefaultMcpClient`） | 自由对接任意 JSON-RPC 服务 |
| 滴滴兼容性 | ❌ SSE 不支持 Streamable HTTP | ✅ JSON-RPC 2.0 完全匹配 |

### 对比：受限于库 API vs 自由扩展

使用 `langchain4j-mcp` 库时，代码中会出现 `HttpMcpTransport`、`DefaultMcpClient`、`ToolSpecification` 等该库特有的类，如果你想接另一个 JSON-RPC 服务或自定义传输层，必须在这个库的框架里打转，它不支持你就做不了。

直调方案只有一个抽象：**RestClient 发 HTTP POST，body 是 JSON-RPC 2.0 格式**。想接什么服务都行，无非是 `method` 名和 `params` 不同。

### 测试验证

已验证通过：

- ✅ `maps_regeocode` 坐标转地址 → 80ms 返回

## 八、MCP 架构重构：可扩展的多源框架（v2.18）

### 动机

旧架构中 `McpClientManager` 同时负责连接管理和工具执行：
- 硬编码了滴滴的 URL、API Key、沙箱配置
- 新增第二个 MCP 源必须改 `McpClientManager` + `McpToolBridge` + `ToolRegistryImpl` 三处

### 方案

引入 `McpSource` 接口抽象 MCP 源，`McpClientManager` 自动收集所有 `McpSource` Bean：

```
McpClientManager（多源管理器）
  ├── toolIndex: Map<toolName, McpSource>
  └── sources: List<McpSource>
        ├── DidiMcpSource  ← "MCP:DIDI"
        └── (未来) xxxMcpSource
```

### 新增 3 个文件

| 文件 | 说明 |
|:----|:------|
| `McpSource.java` | 抽象接口（getSourceName / fetchTools / executeTool / getWriteToolNames） |
| `McpToolDefinition.java` | 独立 POJO（从 McpClientManager 内类拆出） |
| `DidiMcpSource.java` | 滴滴实现（含全部 JSON-RPC 2.0 逻辑） |

### 改 3 个文件

| 文件 | 改前 | 改后 |
|------|------|------|
| `McpClientManager.java` | 单源硬编码 | 多源管理器：`List<McpSource>` 自动注入 + 全局工具索引 |
| `McpToolBridge.java` | 硬编码 `MCP:DIDI` | 遍历所有源注册，WRITE 集合来自各源声明 |
| `ToolRegistryImpl.java` | `if("MCP:DIDI".equals(source))` | `mcpClientManager.executeTool()` 通用路由 |

### 新增一个 MCP 源只需

```java
@Component
public class AmapMcpSource implements McpSource {
    @Override public String getSourceName() { return "MCP:AMAP"; }
    @Override public List<McpToolDefinition> fetchTools() { ... }
    @Override public String executeTool(String name, String args) { ... }
    @Override public Set<String> getWriteToolNames() { return Set.of(); }
}
```

一个文件，零改动现有代码，重启后自动注册。
