## 二、今日开发内容

### 2.1 TTS 语音输出

**涉及文件**: `TtsService.java`、`WechatServiceImpl.java`、`LlmService.java`

#### 方案演进

| # | 方案 | 结果 | 原因 |
|:-:|:----|:----:|:-----|
| 1 | DashScope SDK v1 WebSocket | ❌ | SDK 实际是 v2，API 不匹配 |
| 2 | **DashScope SDK v2 WebSocket** | ✅ **合成成功** | `new SpeechSynthesizer(param, null).call(text)` |

#### 最终数据流

```
用户说"读给我听"
  → LLM 回复末尾加 [VOICE]
  → WechatServiceImpl 检测标记
  → TtsService.synthesize(reply)
  → DashScope WebSocket → CosyVoice 合成 → MP3 byte[]
  → 存 D:\解析文件\voice\yyyy-MM-dd\语音回复_yyyyMMdd_HHmmss.mp3
  → client.sendFile(用户, MP3, "语音回复_xxx.mp3")
```

#### 触发方式

在 LlmService 的 SYSTEM_PROMPT 中新增规则：

```
### 语音输出标记
如果用户要求"说给我听"、"语音回复"、"用嘴说"等需要语音输出的场景，
在回复末尾另起一行加 [VOICE] 标记
```

代码层面用 `contains()` 而非 `endsWith()` 检测，容错 LLM 不严格按格式输出。

#### 关键代码

```java
// TtsService.java — 核心合成
SpeechSynthesisParam param = SpeechSynthesisParam.builder()
        .apiKey(apiKey)
        .model(modelName)
        .voice(voiceName)
        .format(SpeechSynthesisAudioFormat.MP3_24000HZ_MONO_256KBPS)
        .build();

synthesizer = new SpeechSynthesizer(param, null);
ByteBuffer audioBuffer = synthesizer.call(text);
```

```java
// WechatServiceImpl.java — 检测标记 + 存盘 + 发送
boolean useVoice = reply.contains("[VOICE]");
reply = reply.replace("[VOICE]", "").trim();
if (useVoice) {
    byte[] audio = ttsService.synthesize(reply);
    String mp3Name = "语音回复_" + timeStr + ".mp3";
    Files.write(mp3Path, audio);
    client.sendFile(fromUser, audio, mp3Name, "mp3");
}
```

### 2.2 消息持久化 + Session 节点恢复

**涉及文件**: `SessionPrepareNode.java`、`MessageMapper.java`、`MessageEntity.java`、`LlmService.java`、`ToolExecuteNode.java`、`ChatGraphConfig.java`

#### 为什么做

之前消息存在 `ConcurrentHashMap` 里，项目重启后 AI 就"失忆"了。需要把消息存到 MySQL，同时保留内存缓存保证性能。

#### 架构（缓存优先策略）

```
正常对话（缓存命中）：
  WechatServiceImpl → userContexts(ConcurrentHashMap) → 传入图
    → SessionPrepareNode 检测到已有 messageHistory → 跳过查库
    → LlmService 调 DeepSeek → 同时写 MySQL
    → ToolExecuteNode 执行工具 → 同时写 MySQL

重启后（缓存未命中）：
  userContexts 空 → SessionPrepareNode 从 MySQL message 表加载最近 50 条
    → 后续流程同上 → 消息继续累积到 MySQL
```

#### 图结构变更

```
改前（simpleChatGraph）：
  START → prepare_input → llm_think → [tool_execute]

改后（simpleChatGraph + session_prepare）：
  START → prepare_input → session_prepare → llm_think → [tool_execute]
```

#### MessageMapper 核心方法

```java
@Insert("INSERT INTO message (...) VALUES (...)")
int insert(MessageEntity entity);

@Select("SELECT * FROM message WHERE session_id = #{sessionId} ORDER BY id DESC LIMIT #{limit}")
List<MessageEntity> findLatestBySessionId(String sessionId, int limit);

@Update("UPDATE message SET tool_calls = ... WHERE message_id = #{messageId}")
int updateByMessageId(MessageEntity entity);
```

#### 消息角色变更

`MessageRole` 枚举新增 `TOOL`，现在有四个角色：`USER`、`ASSISTANT`、`SYSTEM`、`TOOL`。

### 2.3 网页搜索 + URL 链接读取

**涉及文件**: `ReadUrlTool.java`、`父 pom.xml`、`wechat-ai-tool/pom.xml`、`LlmService.java`

#### 为什么做

同学常问实时信息（新闻、知识问答），AI 不知道最新信息只能瞎编。同时同学也会直接分享链接问"这篇文章说了什么"，需要 AI 能自主阅读网页。

#### 方案设计

两个 @Tool 放在一个文件中：

| 工具 | 说明 | 实现方式 |
|------|------|---------|
| `readUrl(url)` | 读取任意 URL 的正文内容 | Jsoup 抓取 → 提取 &lt;article&gt;/&lt;main&gt;/body.text() → 截断 8000 字 |
| `searchInternet(query)` | 搜索互联网获取实时信息 | Jsoup 抓必应搜索结果 → 解析标题+链接+摘要 → 返回 5 条 |

#### 搜索源选型历程

| 方案 | 结果 | 原因 |
|:----|:----:|:-----|
| DuckDuckGo `html.duckduckgo.com/html/` | ❌ 超时 | 被墙，国内无法访问 |
| **必应中国版** `cn.bing.com/search` | ✅ **正常** | 国内直连，Jsoup 能解析 `.b_algo` 结果 |

#### 数据流

```
用户"搜索最近的AI新闻"
  → LLM 调 searchInternet("AI 新闻 2026年7月")
  → Jsoup → cn.bing.com/search?q=AI+新闻
  → 解析 5 条结果 [标题+链接+摘要]
  → LLM 整理中文回复

用户分享链接 "https://news.qq.com/..."
  → LLM 调 readUrl("https://news.qq.com/...")
  → Jsoup 抓页面 → 提取标题+正文
  → LLM 阅读后回复用户
```

#### SYSTEM_PROMPT 新增规则

```text
## 网页搜索与链接处理规则
- 用户发链接 → 调 readUrl 读取内容，然后回复用户
- 用户问不熟悉的话题、问新闻、问最新动态 → 调 searchInternet 搜索后回答
- 搜索到结果后直接整理回复，不要展示搜索结果链接给用户
- 使用搜索时关键词要准确简洁，尽量用中文关键词
```

#### Jsoup 依赖

```xml
&lt;dependency&gt;
    &lt;groupId&gt;org.jsoup&lt;/groupId&gt;
    &lt;artifactId&gt;jsoup&lt;/artifactId&gt;
    &lt;version&gt;1.18.1&lt;/version&gt;
&lt;/dependency&gt;
```

#### 坑

| # | 问题 | 解决 |
|---|------|------|
| 1 | @Tool 方法忘了加 `public`，`getMethods()` 扫描不到，工具未注册 | 改为 `public String` |
| 2 | DuckDuckGo 被墙，Connect timed out | 换 `cn.bing.com` |
| 3 | 旧 message 表记录了未注册时的 tool_call，重启后报 `tool messages not following tool_calls` | 删除脏数据 |

### 2.4 历史对话搜索 + 消息上限 + 编译参数

**涉及文件**：`ConversationSearchTool.java`（新建）、`ToolRegistryImpl.java`、`ToolExecuteNode.java`、`MessageMapper.java`、父 `pom.xml`、`LlmService.java`

#### 为什么做

三个技术债一起还：

| 问题 | 影响 |
|------|------|
| 对话长了爆 Token | 聊 100+ 轮后 Prompt 越来越大，早晚超 DeepSeek 128k 窗口 |
| 反射参数名 `arg0` | @Tool 方法有多个参数时，LLM 看不懂参数名 |
| AI 不记得之前聊过 | 截断后历史消失，用户问"刚才那个xxx"答不上来 |

#### 方案

**① `-parameters` 编译参数**（1 行 pom.xml）

父 pom.xml 加 `<maven.compiler.parameters>true</maven.compiler.parameters>`，编译后保留原始参数名（`query` 而非 `arg0`）。

**② 消息上限控制 150 轮**（LlmService.think()）

每次构建消息列表后检查。聊天 + 工具调用混合场景下，150 轮 ≈ 够一天正常使用，session 24 小时过期自动重置。

```java
int MAX_ROUNDS = 150;
long nonSystemCount = messages.stream()
        .filter(m -> !"system".equals(m.get("role")))
        .count();
if (nonSystemCount > MAX_ROUNDS * 2L) {
    // 保留 system + 最近的 MAX_ROUNDS*2 条
    ...
}
```

**③ 历史对话搜索 searchConversation**（新建 ConversationSearchTool）

| 工具 | 说明 | 参数 |
|------|------|------|
| `searchConversation(keyword, sessionId)` | 搜索当前会话的历史消息 | keyword（必需，LLM 填写）、sessionId（系统自动注入） |

关键设计：

- `sessionId` 不加 `@P` 注解，**不让 LLM 看到**，由 `ToolExecuteNode` 强制注入
- `ToolRegistryImpl` 跳过无 `@P` 注解的参数（不暴露给 LLM）
- 命中消息前后各取 5 条做上下文，最多返回 3 个片段
- 返回格式：`[用户/AI/工具结果] 内容`

**System Prompt 新增规则**：

```text
## 历史对话搜索规则
- 当用户问"我叫什么"等涉及之前聊天内容的问题时，
  并且当前上下文记不清相关内容
  → **必须先调 searchConversation** 搜索历史记录
- 如果你不确定答案，先调 searchConversation 搜一下
```

#### 坑

| # | 问题 | 解决 |
|---|------|------|
| 1 | `@Tool` 方法缺 `public` 扫描不到 | 加 `public` |
| 2 | LLM 乱填 `sessionId` | 去掉 `@P` 注解，ToolExecuteNode 强制注入覆盖 |
| 3 | 截断太严（3 轮）导致反复搜反复截 | 改为 150 轮，几乎不触发 |

## 三、调试过程记录

### 问题 1：TTS 相关

| # | 错误 | 根因 | 解决 |
|---|------|------|------|
| 1 | `Websocket failure 500: token expected 3 parts` | API Key 过期 | 替换新 key |
| 2 | `Websocket failure 不知道这样的主机 {ws-xxx}` | URL 花括号包住了 ws- 前缀 | 去掉花括号，如 `ws-xxx.cn-beijing.maas.aliyuncs.com` |
| 3 | LLM 不按格式加 [VOICE]（放中间而非末尾） | `endsWith` 太严格 | 改用 `contains` + `replace` |
| 4 | DashScope SDK 编译报错 | 用错了 v1 API（`new SpeechSynthesizer().call(param)`） | 改回 v2 API（`new SpeechSynthesizer(param, null).call(text)`） |

### 问题 2：消息持久化相关

| # | 错误 | 根因 | 解决 |
|---|------|------|------|
| 5 | `HttpClientErrorException 400: missing field tool_call_id` | MySQL 存的 tool 消息缺 `tool_call_id` 字段 | `SessionPrepareNode` 加载时从 `toolCalls` JSON 中提取 `tool_call_id` |
| 6 | `HttpClientErrorException 400: tool messages not following tool_calls` | MySQL `ORDER BY created_at DESC` 同秒乱序 | 改为 `ORDER BY id DESC`（自增主键保证 insert 顺序） |
| 7 | User 消息在 ReAct 循环中重复入库 | 每次 `llm_think` 都调 `saveUserMessage` | 加 `addedUserMsg` 标记，只在真正追加时保存 |

### 问题 3：关键诊断日志

重启后加载的 11 条消息中，msg[7]（assistant ✓tool_calls）和 msg[10]（tool ✓tool_call_id）之间插入了两条无关消息（user + assistant），导致 DeepSeek 报错。根因是 `created_at` 排序不可靠。

## 五、架构决策记录

### 5.1 TTS 方案：DashScope SDK v2

- **决策时间**: 2026-07-20 上午
- **背景**: 需要 AI 能用语音回复用户
- **方案**: 阿里云百炼 CosyVoice + DashScope SDK v2 WebSocket
- **踩坑过程**: v1 API 编译报错（类不在预期包路径下）→ 改用 v2 API（`ttsv2` 包）
- **输出方式**: iLink SDK `sendFile` 发 MP3 附件（`sendVoice` 受协议限制，无语音气泡）
- **依据**: DashScope 走 WebSocket 绕过 HTTP 权限限制；无额外组件依赖

### 5.2 消息持久化：缓存优先策略

- **决策时间**: 2026-07-20 下午
- **背景**: 需要重启后 AI 不失忆，但不想牺牲日常对话性能
- **决策**: SessionPrepareNode 优先检查 state 中是否已有 messageHistory（WechatServiceImpl 从 ConcurrentHashMap 传入），有就跳过 MySQL
- **依据**: 内存读写比 MySQL 快 2-3 个数量级，日常对话不走 MySQL 查询
- **排序坑**: `ORDER BY created_at DESC` 在毫秒级时间戳相同时不保证 insert 顺序 → 改为 `ORDER BY id DESC`（自增主键）

### 5.3 MessageEntity 归属模块

- **决策时间**: 2026-07-20 下午
- **背景**: `MessageEntity` 在 wechat-ai-ai 模块，但 `MessageMapper` 需要放在有 MyBatis 依赖的模块
- **决策**: 从 `wechat-ai-ai/entity/` 搬到 `wechat-ai-session/entity/`
- **依据**: message 表属于会话范畴；wechat-ai-ai 已依赖 wechat-ai-session，引用无阻碍

#### 多机器人集群（设计思路）

**背景**：单微信号有风控限制（频率、并发），且只能在一台设备登录。扩展为多机器人集群可实现负载分担和容灾。

**目标方案**：

```
启动时生成 N 个 ILinkClient（N 个二维码）
  ├── Bot1（微信号A）→ 独立线程池轮询
  ├── Bot2（微信号B）→ 独立线程池轮询
  ├── Bot3（微信号C）→ 独立线程池轮询
  └── Bot4（微信号D）→ 独立线程池轮询

用户消息 → 按 fromUser hash 路由到对应 Bot
          或由 Bot 扫码时绑定固定用户
```

**关键改动**：

| 文件 | 改动 |
|------|------|
| `application.properties` | 加 `wechat.bot.count=4` 或账号列表配置 |
| `WechatServiceImpl` | 改单 ILinkClient 为 Map<botId, ILinkClient>，启动 N 个轮询线程 |
| 用户路由 | 新增路由层：按 userId → botId 分配 |

**前提条件**：

- 需要 N 个可登录的微信号（每个需独立手机号）
- 各微信号需添加目标用户为好友（或用户向各号发消息）
- 注意微信多设备风控（同一 IP 多个号可能触发限制）

**不做的原因**（当前阶段）：

- 单机器人 + session 隔离已能满足团队使用
- 多机器人的运维复杂度（掉线重登、号被封替换、消息路由一致性）远超收益

## 重构：WechatServiceImpl 模块内部解耦

**时间**：下午  
**版本**：v2.7  
**动机**：`WechatServiceImpl` 把登录、轮询、消息分发、文件/TTS、AI 引擎调用全部塞在 335 行，后面再加能力会越来越难改。

**方案**：拆成 6 个职责单一的类，全部位于 `com.wechatai.wechat` 包下：

```
WechatConnectionManager    ← 登录 + 轮询
WechatMessageDispatcher    ← 按 type 分发
WechatInboundHandler       ← 文本/图片/语音/文件处理
WechatChatBridge           ← AI 图调用 + 多轮上下文 + 用户线程池
WechatOutboundSender       ← sendText/sendFile/TTS 统一出口
WechatServiceImpl (瘦身)   ← 只做组件组装（35 行）
```

**调用链**：
```
WechatConnectionManager (轮询)
  → WechatMessageDispatcher (路由)
    → WechatInboundHandler (处理)
      → WechatChatBridge.think() (图调用)
        → WechatOutboundSender.sendReply() (发送)
```

**原则**：业务逻辑零改动，纯解耦，其他模块零影响。

### 二、消息概率性丢失问题排查

**现象**：用户连续发送多条消息时，部分消息无日志无回复地丢失。纯文本、图片+文字、文字+文字均有概率触发。

#### 排查过程

| 尝试 | 改动 | 结果 |
|------|------|:----:|
| `continue` 无间隔轮询 | 有消息时跳过 `sleep(1000)`，立即 `continue` 拉下一批 | 纯文本改善（不丢了），图片+文本仍概率丢 |
| 轮询间隔 1s → 100ms | 无消息时 `sleep(100)` | 无明显改善 |
| 去掉 `continue`，固定 100ms 间隔 | 不管有无消息都 `sleep(100)`，避免无间隔调 SDK | 仍概率丢 |
| `handleImage` 异步化 | 图片下载+QwenVL 识别移到用户线程池 `submit()`，轮询线程瞬间返回 | 纯优化，不解决丢消息 |

#### 分析

纯文本两条也会丢，说明跟图片无关；轮询频率从 1s 改到 100ms、加 `continue`、去 `continue` 都不解决问题，说明不是轮询间隔的问题。

猜测可能是 **iLink SDK 内部的投递机制**（限流/去重/消费确认）导致的，我们在上层能调的参数已经试遍了。

#### 当前状态

未找到根因，推测为 SDK/服务端问题。概率性触发，纯文本场景在加 `continue` 后改善明显，文本+图片仍可能丢。留待后续追查。

### 三、SessionPrepareNode 内存/DB 消息数不一致修复

**问题**：`SessionPrepareNode` 硬编码 `HISTORY_LIMIT = 50`，但 `LlmService` 消息上限为 150 轮（300 条非 system 消息）。当 DB 消息超过 50 条时（缓存未命中，如重启后），从 MySQL 加载最近 50 条消息可能切在 `assistant(tool_calls)` / `tool(result)` 正中间，导致 DeepSeek 400 报错：

```
Messages with role 'tool' must be a response to a preceding message with 'tool_calls'
```

日志确认：消息数=52（非 300+），说明是重建 `messageHistory` 时链断裂。

**根因**：两个常量值不一致（50 vs 150），且没有任何从 MySQL 拼接消息链的完整性检查。

#### 修复（3 处改动）

| 文件 | 改动 |
|------|------|
| `SessionPrepareNode.java:28` | `HISTORY_LIMIT` 从 **50 → 300**（与 LlmService 的 150 轮上限一致） |
| `SessionPrepareNode.java:94-109` | 从 MySQL 加载后，检查第一条消息是否为 `user`。不是则向前找到第一个 `user` 作为起点裁切；全是 tool/assistant 残片则返回空列表让 LlmService 从 system prompt 重新开始 |
| `LlmService.java:193-208` | 截断逻辑后同样做链完整性检查，保证 300 条上限触发时不会送残片给 DeepSeek |

```java
// 链完整性检查（SessionPrepareNode + LlmService 各有一份）
if (!"user".equals(messages.getFirst().get("role"))) {
    // 找到第一个 user 消息，之前全是 tool/assistant 残片 → 丢弃
    int firstUser = 索引;
    messages = messages.subList(firstUser, ...);
}
```
