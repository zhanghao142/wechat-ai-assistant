## 1. 先有一个直觉

把 AI 助手想成一个**会查资料的实习生**，而不是只会背书的复读机。

| 只会聊天的模型 | ReAct 智能体 |
|----------------|--------------|
| 用户问天气 → 模型凭印象编一个温度 | 用户问天气 → 模型决定「该查天气 API」→ 真查 → 再用结果回答 |
| 知识截止在训练数据 | 能调用外部工具拿实时信息 |
| 一次生成完就结束 | 可以：**想一下 → 动手 → 再想一下 → 再动手…** 直到能回答 |

**ReAct** 就是把「思考」和「行动」交替起来的一种工作模式。  
工程上常用 **LangGraph** 这类框架，把循环画成一张「图」（节点 + 边）。

## 2. ReAct 三个字母分别是什么

**ReAct** = **Rea**soning + **Act**ing（推理 + 行动）。

出自论文思路（可后读）：让大模型在回答前显式地：

1. **Reason（推理 / Think）**：我现在缺什么信息？该用哪个工具？  
2. **Act（行动）**：真的去调用工具（查天气、搜文档、发邮件…）  
3. **Observe（观察）**：看工具返回了什么  
4. 再回到 Reason，直到可以给出最终答案  

口语里大家常把整圈叫「ReAct 循环」，本项目里对应：

```text
llm_think  ←→  tool_execute
   推理           行动+观察
```

> 小提示：框架里不一定单独有一个叫 `observe` 的节点；**观察结果**往往写进对话历史，下一轮 `llm_think` 时模型自然能「看到」。

## 3. 为什么不能「LLM 直接瞎编」

大模型擅长语言，但有硬伤：

1. **不知道此刻真实世界**（天气、股价、你刚上传的合同）  
2. **会一本正经胡说**（幻觉）  
3. **不能直接操作外部系统**（发邮件、写文件）——除非你提供工具并让它调用  

所以工业界做法是：

- 模型负责：**理解意图、选工具、组织话术**  
- 工具负责：**查真实数据、执行副作用**  
- 程序负责：**循环调度、安全校验、把结果塞回模型**

这就是 ReAct 在工程里的价值。

## 4. 一轮 ReAct 在干什么（核心循环）

用最简图画出来：

```text
                ┌──────────────────┐
                │  用户说了一句话   │
                └────────┬─────────┘
                         ▼
              ┌─────────────────────┐
              │  Think：问 LLM      │
              │  （带上历史+工具表） │
              └─────────┬───────────┘
                        │
           ┌────────────┴────────────┐
           │                         │
     要调用工具？                  直接能答？
           │                         │
           ▼                         ▼
 ┌─────────────────┐         ┌──────────────┐
 │ Act：执行工具    │         │ 输出最终回复  │
 │ Observe：拿结果  │         │     END      │
 └────────┬────────┘         └──────────────┘
          │
          └──► 把结果写进历史 ──► 再回到 Think
```

要点：

- **可能转很多圈**（查文档 → 不够 → 再搜网页 → 再总结）  
- **每一圈**都是：模型决策一次，或程序执行一次工具  
- **结束条件**：模型不再请求工具，而是给出普通文本回复

## 5. 消息列表：Agent 的「草稿纸」

ReAct 能转圈，靠的是一份不断变长的 **消息历史**（本项目里常叫 `messageHistory`）。

常见角色：

| role | 谁写的 | 作用 |
|------|--------|------|
| `system` | 程序 | 人设、规则、工具使用说明 |
| `user` | 用户 / 程序包装 | 用户这句话（或图片描述等） |
| `assistant` | 模型 | 普通回复，**或**「我要调这些工具」 |
| `tool` | 程序 | 某个工具的执行结果 |

**第一圈（要工具时）大致长这样：**

```text
system: 你是小微，可以调用 queryWeather…
user: 杭州今天天气怎么样？
assistant: （不直接答，而是 tool_calls: queryWeather(city=Hangzhou)）
```

**工具跑完后程序追加：**

```text
tool: {"temp":31,"weather":"阴", ...}   ← 观察结果
```

**第二圈 Think：**

模型看到工具结果，写出最终中文回复 → 程序发给微信。

如果没有这份「草稿纸」，模型第二次思考时会忘掉自己刚查过什么。

## 6. 工具（Tool）是什么

工具 = **给模型用的、有名字和说明的函数**。

模型看不到你的 Java 代码，它只看到类似：

```text
名称: queryWeather
说明: 查询指定城市的实时天气…
参数: { "city": "城市英文名" }
```

模型返回的不是「去执行 Java」，而是结构化请求，例如：

```json
{
  "id": "call_abc",
  "type": "function",
  "function": {
    "name": "queryWeather",
    "arguments": "{\"city\":\"Hangzhou\"}"
  }
}
```

**程序**负责：

1. 解析 `name` / `arguments`  
2. 找到对应 `@Tool` 方法并调用  
3. 把返回值变成 `role=tool` 的消息写回历史  

本项目里：`ToolRegistry` 扫描工具，`ToolExecuteNode` 负责真正调用。

## 7. 和「普通聊天机器人」差在哪

| 维度 | 普通 Chat | ReAct Agent |
|------|-----------|-------------|
| API 调用次数 | 通常 1 次 | 可能多次（每 Think 一次） |
| 是否带 tools | 可以不带 | 通常带工具列表 |
| 控制流 | 线性 | **有环**（Think ↔ Act） |
| 状态 | 可选历史 | **必须**维护含 tool 的历史 |
| 失败处理 | 模型说抱歉 | 工具报错也可写回，让模型换策略 |

可以记一句：

> **Chat = 一次生成；ReAct = 带工具的多轮决策循环。**

## 8. 用生活例子串一遍

**场景：** 用户说「提醒我明天下午 3 点看天气」

理想中的 ReAct（简化）：

1. **Think**：这是提醒；内容里还藏了「到时候要查天气」。设置阶段应调用 `setRemind`，把「查天气」写进提醒内容。  
2. **Act**：`setRemind(...)`（本项目里 WRITE 工具可能先暂停等人确认）  
3. **Observe**：提醒已创建  
4. **Think**：告诉用户「好的，已设好」  
5. **第二天到点**：调度器再触发一轮 AI，新的 ReAct 里再去 `queryWeather`，然后推送

你不必一次记住所有业务，只要理解：**复杂任务 = 多次 Think/Act 组合**。

## 9. 结合本项目：图怎么走

本项目用 **LangGraph4j** 把 ReAct 画成图。结构在：

`wechat-ai-ai/.../config/ChatGraphConfig.java`

```text
START
  → prepare_input        （准备输入，占位/打日志）
  → session_prepare      （会话 ID；必要时从 MySQL 加载历史）
  → llm_think            （Reason：调 DeepSeek）
       │
       ├─ needTool == true  → tool_execute → 再回到 llm_think
       └─ needTool == false → END（最终回复在 state.reply）
```

对应代码逻辑（概念版）：

- `llm_think` 之后用 **条件边**：`state.isNeedTool() ? "tool" : "done"`  
- `tool_execute` **无条件**连回 `llm_think`（形成环）

微信侧不直接懂 ReAct，只通过桥梁调用：

`WechatChatBridge#think` → `compiledGraph.invoke(...)` → 拿 `reply` 发出去。

## 10. 结合本项目：关键类对照表

| ReAct 概念 | 本项目落点 | 一句话 |
|------------|------------|--------|
| 整张循环图 | `ChatGraphConfig` | 定义节点和边 |
| 可执行图 | `CompiledGraph` Bean | 带检查点、可中断 |
| Reason | `LlmThinkNode` → `LlmService.think` | 调 LLM，决定回复或 tool_calls |
| Act + Observe | `ToolExecuteNode` | 执行 `@Tool`，结果写入历史 |
| 草稿纸 | `messageHistory`（state 里） | system/user/assistant/tool |
| 是否继续循环 | `needTool` | true 去执行工具，false 结束 |
| 工具清单 | `ToolRegistry` + 各 `*Tool` | 扫描 `@Tool` 生成 schema |
| 人设与规则 | `LlmService` 的 `SYSTEM_PROMPT` | 告诉模型有哪些工具、怎么说话 |
| 入口 | `WechatChatBridge` | 微信消息进图、回复出站 |
| 图状态 | `ChatGraphState` | userId、sessionId、reply、needTool… |

**节点很薄、服务很厚：**

- `LlmThinkNode` 几乎只做：`llmService.think(state)`  
- 真正拼消息、调 HTTP、解析 tool_calls 的是 `LlmService`

## 11. 走读一次「查杭州天气」

假设用户微信发：**「杭州今天天气怎么样」**

### 步骤 A：进微信模块

1. 轮询收到文本  
2. `WechatInboundHandler` → `WechatChatBridge.think(userId, 文本, "TEXT")`  
3. 组装初始 state：`userId`、`userMessage`、内存里的 `messageHistory` 等  
4. `compiledGraph.invoke(initData, config)`

### 步骤 B：进图前半段

1. `prepare_input`  
2. `session_prepare`：保证有 `sessionId`；若无内存历史则尝试从 DB 加载  

### 步骤 C：第一次 `llm_think`（Reason）

`LlmService.think` 大致会：

1. 确保历史里有 `system`  
2. 追加当前 `user` 消息  
3. 带上工具列表（含 `queryWeather`）请求 DeepSeek  
4. 模型返回 **tool_calls**，而不是最终天气文案  
5. 写入 state：  
   - `needTool = true`  
   - `toolExecutionRequests = [...]`  
   - 更新 `messageHistory`（含带 tool_calls 的 assistant）  
6. 可能把 user/assistant 消息插入 MySQL  

条件边走到 **`tool_execute`**。

### 步骤 D：`tool_execute`（Act + Observe）

1. 读出 `queryWeather` 和参数  
2. 反射调用 `QueryWeatherTool.queryWeather(...)`  
3. 请求真实天气 API  
4. 把 JSON 结果写成 `role=tool` 追加到 `messageHistory`  
5. 设 `needTool = false`（本轮工具做完了；**是否还要工具由下一轮 Think 再决定**）  
6. 边回到 **`llm_think`**

### 步骤 E：第二次 `llm_think`

1. 历史里已有工具结果  
2. 模型据此生成中文回复，例如「杭州目前阴，31°C…」  
3. `needTool = false`，`reply = 那段中文`  
4. 条件边 → **END**

### 步骤 F：出站

`WechatChatBridge` 取 `reply`，`WechatOutboundSender` 发回微信。

## 12. 本项目的增强：WRITE 确认 / Skills

标准 ReAct 之上，本项目还有两层「工程增强」（不影响你先理解主循环）：

### 12.1 WRITE 工具要人确认

- 编译配置了：`interruptBefore("tool_execute")`  
- 进入执行工具前图可以**暂停**  
- 若是发邮件 / 设提醒 / 生成文档等 **WRITE** 工具：先问用户「确认吗？」  
- 用户确认后再 **resume** 同一条执行线程继续 ReAct  

只读工具（查天气等）通常自动 resume，用户无感。

这是 **Human-in-the-loop**，建立在 ReAct 环上，不是另一套模式。

### 12.2 Skills

- 工具很多时，system prompt 会又长又臭  
- `SkillManager`：当上一轮调用了某工具（如天气），下一轮 Think 再**追加**对应 Skill 说明  
- 仍是同一次 ReAct，只是提示词更聪明

## 13. 常见误解

| 误解 | 更正 |
|------|------|
| ReAct = 必须输出一段「Thought:」英文推理 | 那是论文演示格式；工程里「推理」常藏在模型内部，对外是 tool_calls |
| 有工具就是 ReAct | 还要有 **循环**：执行完工具后**再**让模型看结果继续想 |
| `tool_execute` 结束后一定结束对话 | 否，本项目会回到 `llm_think` |
| `needTool=false` 表示永远不再用工具 | 只表示**这一轮** Think 的决策；下一轮用户新消息会重新开始 |
| 微信模块自己实现了 ReAct | 否，微信只负责收发；循环在 `ai` 模块的图里 |

## 14. 自学小练习

### 练习 1（概念）

不看代码，默画：`Think → 要不要工具 → Act → 回 Think`。  
能向同学用「查天气」讲清两圈即可。

### 练习 2（对照仓库）

打开并浏览：

1. `ChatGraphConfig` — 找到条件边和 `tool_execute → llm_think`  
2. `LlmService.think` — 找到 `hasToolCalls` 分支  
3. `ToolExecuteNode` — 找到把结果 `messages.add(resultMsg)` 的地方  
4. `WechatChatBridge` — 找到 `invoke` 之后取 `reply` 的地方  

### 练习 3（日志）

本地跑起来，发「查一下北京天气」，在日志里按时间找：

- `【LLM】返回 N 个工具调用`  
- `【工具执行】queryWeather`  
- `【LLM】回复`  
- `[微信回复]`

把这四条和本文第 11 节步骤对上号。

### 练习 4（进阶思考）

若模型第一轮既想查天气又想搜网页（两个 tool_calls）：

- 图会进入几次 `tool_execute`？  
- 本项目当前是串行还是并行执行多个工具？  

（提示：看 `ToolExecuteNode` 的 for 循环。）

## 16. 一句话收束

> **ReAct = 让大模型在「思考」和「调用工具」之间循环，直到能基于真实观察给出答案。**  
> 本项目用 LangGraph 的 `llm_think ⇄ tool_execute` 实现这条环，微信模块只负责把用户话送进去、把 `reply` 送出来。

如果你能独立讲清第 11 节「查杭州天气」的两圈 Think，说明 ReAct 入门已经过关。
